# 実装×仕様JSON 突合監査（DeepAI）

対象: `origin/main` = `89c38ab`（2026-11-21）。`data/bga-card-specs/` の仕様JSONと、
main にマージ済みの Rust 実装（`src/cards.rs` の `CardDefinition`）とテスト契約
（`data/bga-card-tests/`・`tests/`・`src` 内の単体テスト）を、カード単位で突き合わせる。

これまでの照合は「仕様データ×文献」（Freebuff）と「台帳×仕様×テスト契約」（DeepAI 前回）で
行われてきた。本監査は残っていた **実装×仕様JSON** を埋める。ルールの正本は2016年改訂版
Lookout 公式ルール、カード個別の事実は日本語 BGA アグリコラカード情報 wiki の個別ページ
（`https://agricola.cloudfree.jp/?p=...`）と同サイトの英語一覧を第三者の参照として用いる。
外部のカード説明全文・画像は本リポジトリへ取り込まない（`AGENTS.md` §6）。

## 1. 対象の同定方法（再現手順）

「実装がある」の定義は **`registry::build_default_registry()` に載る `CardDefinition`** とする。
これはゲームが実際に配る・使う定義であり、`src` 内のコメントや未接続の関数ではない。

1. `src/bin` に一時バイナリを作り `build_default_registry()` を走査して
   `external_id / kind / cost / points / effects` を TSV に出す（監査後に削除）。
2. 出力は **77枚**。内訳は A 29 / B 21 / C 10 / D 8 / E 9。
3. `builtin_implemented_cards()`（`src/card_pool.rs`）は帯別プール
   （`verified_band_*_cards`）を含まないため、実装枚数の数え上げには使わない。
   本監査の77枚は `build_default_registry()` と一致する。
4. `src` 内のカードID文字列リテラルで registry に無いものは、単体テスト用の
   ダミー（`A001`/`A004`/`A999`/`E169` 等）と `docs` 内の例示だけで、実装ではない。

未マージ PR のブランチのカードは対象外（例: #389 の A001/A002/A003/A006/A007、
#363 の C006/C007、#392 の A帯 after-worker 追加分）。

## 2. 判定基準

カードごとに次の5点を突き合わせ、判定を付ける。

| 観点 | 仕様JSON | 実装 |
|---|---|---|
| コスト | `play.cost` | `CardDefinition.cost` |
| 前提 | `play.prerequisites` | `CardEffect::Prerequisite` / `can_play` |
| 発火点 | `effects[].trigger` | `CardEffect` の variant と dispatcher の phase |
| 対象 | `target` / `conditions` | variant の `space` / `good` / owner 固定か any-player か |
| 得られるもの | `steps[].operation`+`params` | variant の `amount` / `rule` |

判定区分:

- **一致**: 5点すべて同じ。表現（`MinimumPlayers` と `bga.eligibility` など）が違うだけの
  ものは「表現差」として別に記録し、不一致に数えない。
- **不一致**: どちらかが文献と食い違う。文献で決まる場合は、間違っている側
  （仕様・実装・テスト契約）を直す。
- **仕様未作成**: `data/bga-card-specs/<ID>.json` が無い。突合できないため、
  実装を文献とだけ照合し、仕様作成の担当範囲と重複しないよう記録に留める。
- **文献未確定**: 文献だけでは決まらない。推測で確定せず、人間チェックリストへ送る。
- **他PR進行中**: 同じファイルを未マージPRが編集中。二重作業を避けるため記録のみ。

## 5. 横断所見

### 5.1 `post_play: left_neighbor_hand` がエンジンに無い（P1）

仕様側は使用後のカード移動先を `post_play.destination` に独立して記録しており、
実装済み77枚のうち次の10枚が `left_neighbor_hand`（自分の前ではなく左隣の手札へ）である。

`A005 A008 B006 B007 C004 C005 D004 D005 E007 E008`

main のエンジンには「使用したカードを左隣の手札へ移す」経路が無く、これらは
**自分の前（played_cards）に残る**。カードの印刷点はすべて0なので得点差は出ないが、
カードの所有が変わるため「小さい進歩がない」条件（E111 世捨て人）や、
以後の効果参照（自他の `played_cards`）に影響する。

仕様データ全体では85枚が `left_neighbor_hand` を持つ（A001–A009 など帯の共通機構）。
したがって1枚ずつの実装ではなく、**カードゾーン基盤の追加機能**として扱う必要がある。
この不足は既存 Issue **#365**「カード使用後の左隣へ受け渡し（post_play destination）」が
追跡しており、本監査は #365 の対象カードを「実装済み10枚 + 仕様85枚」へ更新する根拠を
提供する。仕様・テスト契約は文献どおりのまま維持する（実装側に合わせて書き換えない）。

### 5.2 registry の人数別定義の畳み込み（P1・#368で進行中）

`verified_*_cards(players)` は人数別に定義を返すが、`build_default_registry()` は
2→3→4人の順に `seen` で重複を落とすため、**先に追加された2人用定義が3〜4人戦でも使われる**。

- `B121` 地質学者: 3人以上で「粘土坑」も対象（文献）だが、registry は2人用定義
  （森林・葦原のみ）を採用する。
- `B102` 女性顧問: 2/3/4人でレンガ3/葦2/羊2（文献）だが、registry は2人用の
  レンガ3のみを採用する。

カード定義側（`src/cards.rs`）は文献どおりに人数別を持っているため、実装の誤りではなく
**組み立て側の欠落**。未マージの #368 が同じ問題を扱っているため、本監査では変更しない。

### 5.3 「人数適格」の表現差（不一致ではない）

`A133`（3人以上）/`A143`（3人以上）/`A155`（4人）/`B142`（3人以上）/`B144`（3人以上）は、
実装が `CardEffect::Prerequisite { MinimumPlayers(n) }` を持ち、仕様は
`bga.eligibility` に同じ人数制限を記録している。`can_play` は `MinimumPlayers` を
常に真として扱い（`cards.rs` / `card_events.rs` とも）、配布プール側の制限として働く。
同じ事実の表現差であり、不一致に数えない。ただし `MinimumPlayers` が
「カードの前提」と「デッキ適格」の二役を兼ねている点は設計上の負債として記録する。

### 5.4 語彙の揺れ（仕様側・別Issue）

一部の仕様は語彙表（`docs/bga-card-effect-vocabulary.md`）にない trigger を使う。
例: `B098`/`B099` の `trigger: "game_end"` と `steps[].params.amount`
（語彙表は `end_scoring` と `gain_points` + `params.points`）。仕様内部の揺れであり
実装との不一致ではないため、本監査では触らず語彙統一Issueへ送る。

## 6. 人間チェックリスト（文献だけでは決まらない）

- **Q-0 C005 進歩の範囲（既存 #349）**: 仕様の unresolved と Issue #349 が既に
  「`count[improvement]` が小進歩を含むか大進歩のみか」を人間決定待ちにしている。
  本監査でも同じ結論（実装・テスト契約は小進歩を含む、文献は「大きい進歩」のみ）に
  到達したため、**決定せず** #349 の判断材料として日英の文言を追記する。
- **Q-1 A042 森林の範囲**: 仕様・実装は「森林/小森/林」の3スペースで食料1。
  日本語ページ・英語一覧はともに「森林（Forest）」とのみ書く。A116 木こりは
  同じwikiで「木材の累積スペース」と書き分けており、A042 は森林1スペースの読みが自然。
  本監査は文献に合わせて実装・仕様を森林のみへ狭めた（第1章）。逆の読み
  （3スペース全部）を採る場合は第1章の変更を戻す必要がある。
- **Q-2 A101 調理進歩の範囲**: 文献の寸評は「掘り土窯・東洋かまども1点になる」と補足する。
  エンジンの `Improvement` は基本の大進歩10種のみで、カード由来の調理進歩を表現できない。
  数え方（カード進歩を含めるか）と、含める場合の基盤追加を決める必要がある。
- **Q-3 C005 レンガの部屋**: `clay_room_count` はレンガ家・石家の部屋を数える。
  文献は「レンガの部屋1つにつき」。石の家の部屋（石材の部屋）を数えるか未確定。
  #349 の決定時に併せて確認する。
- **Q-4 B006 「人物の数」**: 仕様・実装は総家族数（`FamilyMembers`）。文献は
  「あなたの人物の数」。配置済みワーカーを含むかは Issue #351 が人間決定待ち。
  本監査では変更しない。
- **Q-5 E113 家族を増やすアクションの範囲**: 実装は増員3スペースに限定。文献は
  「アクション」全般で、カード効果による増員を含むかが不明。
- **Q-6 E118 食料を得るアクションスペースの範囲**: 実装は4スペース固定。文献の寸評は
  「アーチ道・森の宿屋でも発動する」とカードスペースを含む。汎用フックが必要。
- **Q-7 D034 石の家ボーナスの排他**: 文献は「石の家によるボーナス点は1枚のカードからのみ」。
  エンジンは1枚ごとに加算するため、同じ条件のカードを複数持つと二重計上になる。
  排他の実装方法（最大値のみ採用か、選択制か）を決める必要がある。
- **Q-8 B107 ラウンドスペースへの配置**: 文献は「残りの各ラウンドスペースに食料3を置き、
  そのラウンド開始時に得る」。実装は「石の家に住んでいる間、毎ラウンド開始時に食料3」。
  ラウンド開始時点の評価としては同値だが、表現の同一性を確認してほしい。
- **Q-9 post_play 左隣の手札**: 5.1 の基盤Issueの実装方針（移動先のデータ表現、
  移動先プレイヤーの手札に入ることで観測・保存・AI秘匿に与える影響）。
