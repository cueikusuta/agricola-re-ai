# M10 4人戦カードプール実装計画（Issue #105）

更新: 2026-11-06。**計画のみ。未監査カードを実装済み・配布可能と見なさない。** カード原文・画像は収録しない。

## 1. 現状と規模

- PR #102 の一次CSVは840行、A〜E各168、職業420、通常小進歩416、複合4（A060/D025/D059/D060）。A/B基本フラグ96。ID欠番0、重複0。840行すべて `自動一次分類`。
- `src/cards.rs` に34 IDが現れ、台帳は「コード内定義30＋2人戦プリセット外4」と分類。しかし**4人戦の人数適格と正しい効果は現時点で未認定**。2人戦用30枚をそのまま「4人戦配布可能」としない。
- CSVに人数条件フィールドがなく、838行は同じ非公式総合出典URL、D025/D159が別の非公式一覧。実装可否の事前ゲートは Issue #115 に分割。
- `CardDefinition` は `Occupation` / `MinorImprovement` の二値で、共通 `CardEffect` は `OnPlayGain`, `AfterWorkerGain`, `StartRoundGain`, `HarvestFieldGain`, `Passive`, `Prerequisite`, `EndGameBonus` 等。複合種別のカードには新型/選択式の設計が必要。 `CardSet::validate(players)` は現状 `MinimumPlayers` と7枚×人数を確認するが、すべての人数制限を意味的に保証するものではない。
- **注意**：A005は台帳上の「他プレイヤー・難度5」が現行コードの自己粘土依存 `OnPlayGainPerStored` に対応しない。自動タグを実装順の確定根拠にしない。A055は #91で公式照合待ち。

## 2. デッキに採用する厳密なゲート

`Eligible4(card)` =
1. `kind` が職業/小進歩として一意に確定。複合種別は専用実装・検証が終わるまで除外。
2. 4人戦で合法な人数条件・プレイ制限が公式根拠とテストで確定。
3. 費用/点数/発動時点/任意-強制/対象/他カードとの相互作用が個別照合済み。
4. Rust実装が存在し、合法使用・不正使用・非発動・保存/復帰・再演・非公開情報テストに合格。
5. 4人で重複のないセットを配布できる。

`usable_occupations_4p`、`usable_minors_4p` を **上記を満たすユニークID** で別々に集計。未検証・未実装・2人戦でのみ検証済み・公式疑義ありは加算しない。小進歩/職業が同一IDを兼用する場合、双方を同時にカウントしない（厳密なカード消費制約を持つ専用型が必要）。

## 3. 順序と達成ゲート

| ゲート | 適法に配れる職業 | 適法に配れる小進歩 | 受入 |
|---|---:|---:|---|
| G1 初期4人10-7成立 | 40 | 40 | 独立した4人10-7の配布40+40、合法性・効果個別テスト・全試合再演 |
| G2 実戦用の多様性 | 80以上 | 80以上 | 同ゲートに加え効果系統・カード組み合わせの多様性、AI評価偏り検査 |
| G3 長期拡張 | A〜Eで確認済みの全カード | 同左 | 840件から合法・非該当の理由を明示し、未監査/未実装と区別 |

G1の40枚は配布上の最低必要数であり実戦的なシャッフルの多様性を保証しない。G2の各80枚も強さ・バランスの完成宣言ではない。G1の枚数チェックは **`Config.players=4` × `draft_10_7` で有効なプール上**で行う。

## 4. 選定アルゴリズム（公式照合後に採用）

### 4.1 候補の個別監査順
1. 既存34 IDのうち4人適格・効果正確性が確認できるもの（再使用率の高い共通フックから）。`implementation_reference` は仮の参照情報。
2. A/B中心に難度1〜3と推定された候補を**人手で再分類**。A〜E全体から偏りを補正する。
3. 最低4系統（即時、ラウンド/ワーカー/収穫時、持続割引/容量、条件付き/終了時得点）を職業・小進歩**それぞれで**確保。複雑な効果が必要な場合でもカードIDを増やすための誤実装をしない。
4. 4人に関与する効果（他人、相対順位、手札移動など）は別型・別Issueで検討。正しく検証できるまで配布しない。

### 4.2 多様性スコア
`family_coverage = distinct_implemented_effect_families / distinct_verified_candidate_families`（分母の定義もカード台帳の正式監査で固定）、
`dominance = max_family_count / total_usable_kind`、
`interaction_coverage = verified_interaction_pairs / planned_interaction_pairs` を職業・小進歩ごとに測る。暫定G1目標は**各種別4系統以上、最多の系統が50%未満**（公式監査の結果、候補が足りないなら未達として報告）。G2目標は各種別6系統以上、最多40%未満を検討。異なる効果がある場合、主効果のほか複数タグを保持し、1カードを複数枚に数えない。

### 4.3 小さな実装単位（1 Issue = 1目的 = 1ブランチ = 1PR）
- **M10-DATA**：カード台帳の個別出典・人数適格・照合状態（既存 #115、新規重複Issueを作らない）。
- **M10-CORE**：`eligible_at_player_count`、型・配布フィルタ・検証済みフラグとG1/G2集計。M8-2の合法性検証器とは別契約。
- **M10-EARLY-01/02**：各8〜12枚を上限とする即時獲得／明確な費用・前提の単純カード群（職業と小進歩を混ぜても各種別件数を集計）。
- **M10-PASSIVE-01/02**：各8〜12枚の持続割引・収容力・収益。
- **M10-TRIGGER-01/02**：各8〜12枚のワーカー後・ラウンド・収穫時イベント、効果競合の順序をテスト。
- **M10-SCORE-01/02**：各8〜12枚の条件付き・終了時得点、ゲーム終了までの差分検証。
- **M10-INTERACTION**：複数効果フックの順序、複数カードの競合、同時発火の検証だけを目的に分割。
- **M10-ADVANCED**：難度4〜5、他人への影響、盤面移動、カード譲渡、兼用カードなどを**仕様ごとに別Issue**。未確定公式ルールは隔離。

上の接尾番号は**Issue作成前の分割案**。監査で実装可能な個別カードを8〜12枚選んでから、実際のID・公式参照・発動テストを明記してIssue化する。数合わせの先行Issue乱立を避ける。

## 5. テスト要件

- カードID単位：`CanPlay`（4人の人数適格、費用、前提）、`OnPlay`、発動/非発動の各条件、任意/強制選択、正しい数量・得点。
- フック単位：カードをプレイした順と発動順、同じイベントを複数カードが参照した場合の決定的順序、相互作用（職業×小進歩、カード×主要改善、他人/自分）。
- デッキ単位：全ID一意、4人に40+40を配布、許可プレイヤー数以外拒否、複合カードや未確認を排除、固定seedで同じ配布。
- 対戦単位：4人戦14ラウンド、収穫/給餌・保存/復元・再演ハッシュ・観測秘匿・使ったカードの正確な得点。
- UI/AI：日本語カード名/自作概要、合法ピック/使用/非使用、説明と実装の乖離、Playwrightで手動選択と失敗入力、対CPUとの完走。
- CI：通常60秒目標の軽量単体テストと、GitHub Actions専用大量試合 (#110) / ブラウザ長時間 (#92) を分離。
