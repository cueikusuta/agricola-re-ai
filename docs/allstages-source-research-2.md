## 2. 第2章 追加の典拠集め

### 2.1 公式ルールと公式付録（等級A）

**公式ルール（2016 RE, 英語）**

- ラウンドの手順は「労働フェイズ → 帰宅フェイズ → （収穫のあるラウンドなら）収穫」の順で、
  **帰宅フェイズは収穫とは別の段階**として明記されている。人物を部屋に戻す段階である。
  段階3の「帰宅フェイズ」基盤が、ラウンド終了イベントに混ぜられない根拠になる。
- 収穫は「畑フェイズ → 食料供給フェイズ → 繁殖フェイズ」の3段階。
  段階4の P4（反復＋得点）が畑フェイズ・供給フェイズを分けて扱う根拠になる。
- 得点では、食料・作物を「ストック・畑タイル上・カード上」のすべてから数えると書かれている。

**公式付録（用語集）**

- **畑（field）は、畑タイルと、自分を畑と明記しているカードの総称**である。
  「畑がない（No Fields）」は、畑と明記した小進歩も含む。
  一方、「畑タイルがない（No Field Tiles）」は盤上の畑タイルだけを指す。
- **農場スペースが使用済み**になるのは、そこにタイルか厩が置かれたときである。
- 「畑のように機能するが、畑と明記していないカード」は畑ではない。

この3点から、Q-1 の主要部分は公式テキストで説明できる。

1. カード畑は**畑としては数える**（畑の数、畑を条件にする効果、収穫、得点）。
2. カード畑は盤上のタイルではないため、**農場スペースを1つ使うわけではない**。
   未使用スペースの減点にも影響しない。
3. 柵・牧場・厩の配置は盤上のスペースの話であり、カード畑はそこに割り込まない。
4. 「畑のように機能する」だけのカード（B072 の牧場など）は、自分を畑と明記しているかを
   個別に確認する必要がある。B072 は「牧場は畑でもある」と明記するため畑に数えるが、
   盤上の牧場スペースとの重なりは別問題として残る。

**残る不明点**: カード畑が「畑1つ」として数えるときに、複数作物の重なりや
「畑1つにつき」の効果でどう数えるか。付録はそこまで書いていない。

### 2.2 公式FAQ（等級A）

公開アーカイブで取得した公式FAQの内容は、次の3点だけだった。

- 旧版と改訂版の拡張セットの混在は「プロ向けなら可能」。統一された文言と作り直されたカードのため、
  混在は問題を起こしうる。
- 改訂版は1〜4人用。旧版の1〜5人用から、5〜6人用拡張を別売りする形に変わった。
- 5〜6人用拡張の位置づけ。

**カード個別の裁定は無い**。したがって、公開されている公式情報でカードの細部を決めるには、
ルールブック付録の用語集と、印刷カードの文言・アイコンが上限になる。
「公式FAQを探せばカード裁定がある」という前提は、この版では成り立たない。

### 2.5 カードDB（等級C）

Mark Hartnady 氏のカード一覧（1,702枚）で、D025 と D159 の本文を確認した。
D025 は「畑・職業・かまどの大進歩」、D159 は「葦1→食料3、他者は食料2で購入、最大8」。
コンペンディウムと一致する。DBの `insight` 欄は空で、追加の裁定は無かった。

### 2.6 版差・旧版との比較（等級C）

- **D025**: 旧版のカードには品物→食料の変換が印刷されていたが、改訂版では ERRATA で
  変換を削除し、調理場との交換だけが残る。旧版の記述をそのまま使うと過大になる。
- **A136**: コンペンディウム（1/3/6/9）と印刷カード（3/6/9）が食い違う。
  印刷カードが正本に近いが、版によって文言が変わった可能性がある。公式確認待ち。
- **B043**: 旧版の同種カード（料理店）の裁定は「小麦3/野菜2」で、改訂版と一致する。
- **A060**: 旧版からの「小進歩/大進歩のどちらか1つ」の裁定が改訂版にも引き継がれている。

### 3.3 統合側への申し送り（分類は決めない）

- 段階1の13枚は、**A060 を「返却費用」の別類型**として残すか、資源ORと同じ段階1に含めるかで
  実装の入口が変わる。Q-8 の「どちらか1つとして数える」は、置き場所の設計に影響する。
- E052 の費用は仕様の代替注記と印刷が違う。段階1の費用選択の実装では、印刷側を採る。
- C070 はカード畑である。段階2の畑の集合に含めるかは統合側の判断。
- D025 は畑・職業・大進歩の複合、D159 は anytime＋他者参加。どちらも「保留」から動かせる。
- A136 は仕様注記を直す。C038 は仕様の登録を直す。B069 は英語一覧を直す。
  いずれもコード変更ではなく、仕様データの修正として別Issueに分ける。
