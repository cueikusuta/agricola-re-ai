# カード実装供給・レビュー・作業単位の運用方針

共通原則はルート直下の [`AGENTS.md`](../../AGENTS.md) を参照する。本書は Issue #530 で決定された、カード実装の供給・レビュー・作業単位に関する運用方針の正本である。ゲームルール、カード仕様、公式典拠の優先順位を変更するものではない。

## 1. 決定事項と適用状態

### 1.1 補充・優先順位・復帰の決定スクリプト化

- 補充、優先順位付け、障害からの復帰の判定は、決まった動作を実行するスクリプトへ寄せる。
- 運転役は、スクリプトで扱えない例外の判断だけを担当する。
- 詳細な設計と実装は別セッションで行う。この方針記録だけで、既存の自動化が変更済みになったとは扱わない。

### 1.2 仕様・テスト契約・CI を主役にしたレビュー

- レビューの合否は、仕様とテスト契約、および CI の結果を中心に判定する構成へ移行する。
- LLM によるレビューは、契約では表現できない変更へ限定する構成へ移行する。
- 移行の設計と実装は別セッションで行う。別の変更が統合されるまでは、現行の独立レビュー、再レビュー、CI、マージゲートをこの方針だけを理由に省略しない。

### 1.3 仕組み単位のバッチを既定にする【即時適用】

- 新規のカード実装 Issue・Kanban カードは、共通する仕組みを持つ複数カードのバッチを既定とする。
- **1枚だけのカード実装 Issue・Kanban カードを新規に切らない。**
- 既存の実装・修正・レビュー・競合解消・復帰カードを遡って再編しない。この即時適用は新規のカード実装カードに対するものである。

## 2. 新規実装カードの切り方

1. 共通の trigger、event、状態遷移、エンジン語彙、または検証基盤を必要とするカードを一つのバッチにまとめる。
2. 1 Issue = 1 ブランチ = 1 PR を維持する。一つの Issue に複数の独立した成果物を混ぜない。
3. 各 Issue・Kanban カードには、少なくとも次を明記する。
   - バッチを束ねる仕組みと対象カード ID
   - 対象ファイルと完了条件
   - ワーカー間で共有する型・関数・語彙・数え方などのつなぎ目
   - カードごとの仕様・テスト契約と必要な CI
4. 既存の実行時間制約内で完了できる粒度に分割する。大きな仕組みは、関連性を保った複数カードのバッチへ分割し、実行時間超過や無関係な仕組みの混入で解決しない。
5. 既存語彙で表現できないカードを近似実装しない。必要な語彙拡張・エンジン改修を、その能力を必要とする複数カードの仕組みバッチとして計画する。
6. 一つの仕組みに1枚しか残っていない場合も単独では新規起票しない。共通の語彙拡張や検証基盤を持つ後続カードとまとめ直す。

## 3. 今後の作り替えとの境界

決定スクリプトへの移行とレビュー導線の移行は、別途実施する作り替えの対象である。本書の導入ではスクリプト、CI、レビュー手順の実装を変更せず、即時適用が指定されたバッチ既定だけを通常運用へ反映する。
