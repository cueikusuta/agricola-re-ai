# ボーナス点 残り4枚の解放条件（C098 / C099 / D099 / A100）

- 対象: `cueikusuta/agricola-re-ai`
- 基準: `origin/main` = `1a176a0`（2026-11-17）。ボーナス点スタックの現状も同日に確認。
- 目的: PR #344 で「別の基盤が不足しているため実装停止」と判定された4枚について、
  **何が揃えば実装を開始できるか**を、コードの現状・文献・テスト契約まで分解して記録する。
- 方針: 本文書は調査と解放条件の定義のみ。Rust・仕様 JSON・テストは変更しない。
- カード効果は第三者の BGA アグリコラカード情報 wiki（日本語個別ページ・英語一覧）を
  照合した**自分の言葉の要約**。原文・画像は転載しない。正本は2016年改訂版 Lookout 公式ルール。

## 0. 結論

4枚は「ボーナス点の持ち場」だけでは解放されない。**ボーナス点の台帳は前提の一部**であり、
本体は次の4つの位相・決定基盤である。

| カード | 本体の不足 | 必要な基盤 | 開始できる条件 |
|---|---|---|---|
| C098 サイコロ彫り | 収穫の畑フェイズ中の任意支払い | 収穫トランザクション（停止・再開） | G0 + G1 |
| C099 ガーデンデザイナー | 得点計算開始時の食料配置の決定 | 得点フェイズの意思決定 | G0 + G3 |
| D099 土器作り | プレイ時ラウンドの記録＋最終収穫後の任意支払い | G1 + 最終収穫後フェイズ | G0 + G1 + G2 |
| A100 後見人 | 帰宅フェイズ＋プレイヤー別の使用スペース | 帰宅フェイズと使用履歴 | G0 + G4 |

**G0（ボーナス台帳の一本化）が現在赤**である。`feat/deepai-bonus-point-store` の HEAD
`1caa250` はテストターゲットがコンパイルできず（E0061 が20件）、#332 は古い base
`308ce83` の上にあり CONFLICTING。この状態で4枚を積むと、後から台帳のハッシュ契約が
変わって再演・固定ハッシュのやり直しになる。まず G0 を緑にし、その上で G1〜G4 を
1基盤=1PRで積むのが最短である。

## 1. 現在地（2026-11-17）

### 1.1 main の状態

- `Game` に `bonus_points` は無い。`Player.card_points` は**プレイ済みカードの印刷点**の
  合計で、`CardState::validate_card_points` が不変条件を検査している。効果で得た点を
  ここへ足すことはできない。
- `score()` は `&Player` だけを受ける純関数。`score_with_cards` は
  `cards::end_game_bonus` を足すが、**得点計算中の意思決定**は扱わない。
- `harvest()` は畑→給餌→繁殖を一括で解決する。`harvest_fields()` は
  `dispatch_harvest_field` の `Transition::Paused` を `.expect(...)` で捨てている。
  現存カードに畑フェイズ中断効果が無いため実害は無いが、C098 が最初の該当例になる。
- `pending::Continuation` は `PostWork` のみ、`ChainStep` は
  `AfterHarvestBake / AfterClayConstruction / AfterWorker` の3種。
- `PublicState.used` は `BTreeSet<Space>` で、**誰が**そのスペースを使ったかを持たない。
- `Player.played_cards` は `Vec<String>` で、**いつのラウンドに出したか**を持たない。
- `start_round()` は `used` と `card_uses` を消し、`pending` を持ち越さないことを
  `debug_assert` で禁止している。帰宅フェイズは独立した地点として存在しない。

### 1.3 PR #344 の停止理由の再確認

#344 の判定は現在も妥当である。ただし「ボーナス点の持ち場が無い」のではなく、
**持ち場の外側の位相が無い**ことが本体である。C098 の「出したとき木材1」だけを入れれば
コンパイルは通るが、本体の任意交換が無いカードをプールに入れると対戦結果がルールと
食い違うため、部分実装はしない（#344 と同じ方針）。

## 2. 共通ゲート

### G0: ボーナス台帳の一本化（全4枚の前提）

1. #327 の HEAD `1caa250` のテストコンパイルエラー20件を直す。
   `cards::play` / `apply_on_play_effects` / `dispatch_play` の呼び出し側を
   `bonus_points` 引数に合わせる。CI を緑にする。
2. #332 を `1caa250`（または修正後の #327 HEAD）へ rebase し、CONFLICT を解消する。
   #328 も同様。**#327 → #328/#332 の順**を守る。
3. 台帳を `state_hash` に入れるか、`integrity_hash` だけにするかを確定する。
   推奨は `1caa250` の「非空のときだけ domain separator 付きで `state_hash` に追記」。
   空台帳の v5 互換を保ちつつ、ボーナス点の改竄・再演食い違いを検出できる。
4. E100 の H-1（OR/AND）を決めるか、E100 を台帳PRから分離する。
   4枚の解放だけなら分離を推奨。E100 の解釈で4枚の実装は変わらない。
5. `Game::validate` / `validate_incremental` / `validate_free_action` が台帳の
   不正な加点を拒否することを、4枚の実装前後で再確認する。

**G0 の完了条件**: `cargo test --locked` が緑、#327/#332 の固定ハッシュテストが最新 HEAD で
緑、`state_hash` の契約が `docs/rule-decisions.md` に記録されている。

### G1: 収穫トランザクション（C098 / D099）

現状の `harvest()` は一括解決で、途中で停止できない。必要なもの:

- `HarvestStage`（Field / Feeding / Breeding / End）と、現在のプレイヤー・残りのプレイヤー・
  効果位置を持つ `HarvestCompletion`。
- `Continuation::Harvest { stage, player, completion }`。給餌・繁殖計画
  （`Vec<FeedingPlan>` / `Vec<BreedingPlan>`）を凍結して保存する。既存の
  `WorkCompletion` と同じ「一時停止中の状態を保持する」契約。
- `harvest_fields()` が `dispatch_harvest_field` の `Transition::Paused` を
  **捨てずに返す**。`harvest()` も `Result<Transition>` に変え、`next_worker_or_round` が
  Paused を伝播する。`finished` / `start_round` は再開後にだけ実行する。
- 保存・復元・再演: `pending` と `HarvestCompletion` を `integrity_hash` に含め、
  `state_hash_before` の一致を検証する。`LOG_VERSION` は据え置き、新規フィールドは
  `serde(default)` で旧セーブを読む。
- イベントログ: 畑フェイズの効果は `before` / `after` を持ち、再開後の
  `pending_resolution` が最終状態までを覆う。既存の `PostWork` と同じ方式。

**G1 の完了条件**: 収穫の途中で停止し、保存→復元→再開→給餌→繁殖まで到達する
固定シードテストが緑。Paused を捨てる `.expect` が無くなる。

### G2: 最終収穫後フェイズ（D099）

#332 は `dispatch_harvest_end` を収穫の後（ラウンドが進む前）に呼ぶ。D099 はこの地点を
使えるが、**任意支払い**なので `Result<()>` の決定的付与では足りない。

- `dispatch_harvest_end` を `Result<Transition>` にし、`pending` と `bonus_points` を受け取る。
  または、最終収穫専用の `dispatch_final_harvest` を追加する。
- `public.round == 14` のとき、`harvest()` の後・`finished = true` の前に D099 の
  意思決定を挟む。`next_worker_or_round` は Paused なら `finished` を立てず、
  再開後に立てる。
- 支払いは `0..=family` のレンガ。1点につき1レンガ。台帳の発生元は `D099`。
- E099（収穫終了の自動点）と同時に発火する。2016年改訂版 p.8 の同時効果の解決順は
  アクティブプレイヤーが選ぶ。D099 は任意なので、E099 の後に選んでもよい。

**G2 の完了条件**: ラウンド14の最終収穫後に停止し、0〜家族数の支払いを選び、
得点計算へ進む。保存→復元→再開が緑。

### G3: 得点フェイズの意思決定（C099）

`score()` / `score_with_cards()` は純関数で、得点計算中の選択を扱わない。必要なもの:

- `ScoringPlan`（プレイヤーごとの「空き畑に置く食料」の割り当て）。各畑は 0 / 1 / 4 / 7 の
  いずれか、合計は食料在庫以下。1/4/7 の畑1つにつき 1/2/3 点。
- `score_with_cards_and_plans(players, cards, plans)` と、`Game::standings` の plan 版。
  `card_bonus` カテゴリに C099 の点を足す。`cards` カテゴリ（印刷点）は不変。
- 得点フェイズのループ（プレイヤーごとに plan を決める）。エンジンに phase を足すか、
  CLI/Web が得点直前に plan を集めてから `score` を呼ぶ。人間UIには割り当て画面が要る。
- AI は終局なので、空き畑数・食料・1/4/7 の効率から最適割り当てを DP で解ける。
  ただし「人間が選べる」API を先に作り、AI 最適化はその上に載せる。
- 空き畑の定義: `Tile::Field { crop: None }`。**カード畑（第2部の B068/B113/B141/E068/E069）を
  「畑」に数えるか**は第2部 Q-1 に依存する。数えるなら C099 の plan の対象に含める。

**G3 の完了条件**: 空き畑0/1/2/3、食料0/1/4/7/8/14 の組み合わせで、合法 plan の列挙・
検証・得点が一致する。カード畑を含める場合はそのテストも緑。

### G4: 帰宅フェイズと使用スペース履歴（A100）

- 帰宅フェイズは現状のエンジンに無い。`next_worker_or_round` の「労働フェイズ終了」と
  `start_round` の間に `end_round()` を置く。ラウンド14では `finished = true` の前に置く。
- `start_round` は `used` を消すので、A100 は**その前**に解決する。`pending` を
  持ち越さない契約は維持し、`end_round` の中で停止・再開を完結させる。
- プレイヤー別の使用スペース: `PublicState.used` は集合だけなので、
  「自分が累積スペースから戻した人数」を数えられない。選択肢は2つ。
  - **A**: `PublicState.used_by: BTreeMap<Space, Vec<usize>>` を追加する。公開情報で、
     `state_hash` に入る。カード有りの既存固定ハッシュが変わるため、v5 互換の判断が要る。
  - **B**: `Game.round_placements: Vec<(usize, Space)>` を bookkeeping として持ち、
    `Observation` には派生した `return_home` 情報だけを出す。`state_hash` には入れず、
    `integrity_hash` と `validate` で整合性を検査する。`search_clone` にコピーする。
    保存時はイベントログから再構築できるが、`search_clone` はログを持たないため
    フィールドのコピーが必要。
  - 推奨は **B**（v5 固定ハッシュを守り、A100 のためだけに全カードゲームのハッシュを
    変えない）。ただし再演の `state_hash` だけでは履歴の食い違いを検出できないため、
    `validate` と `integrity_hash` の検査を追加する。
- 「累積スペース」の判定: `Space::accumulation()` は動物市場（羊/猪/牛）に `None` を返す。
  A100 の「累積スペース」は動物市場を含むため、`is_accumulation_space()` を新設し、
  `accumulation().is_some() || matches!(SheepMarket|PigMarket|CattleMarket)` とする。
  カードが作る累積スペースを含めるかは §5 H3-2。
- 1ラウンド1回。`card_uses` の `use_limit: Some(1)` で表現できる。`start_round` で
  `card_uses` が消えるため、帰宅フェイズはその前に行う。
- 支払いは食料1。台帳の発生元は `A100`。複数プレイヤーが条件を満たす場合、各自が
  1点を買える（食料は各自の在庫）。順序は得点に影響しない。

**G4 の完了条件**: 2/3/4人で、累積スペースに3人以上/2人以下を置いた場合の
帰宅フェイズ判断、食料の支払い、ラウンド14、保存→復元→再開が緑。

## 3. カード別の解放条件

### C098 サイコロ彫り

- 効果（要約）: 出したとき木材1。各収穫の畑フェイズに、木材1＋食料1をボーナス1点に
  交換できる（任意）。
- 典拠: 日本語個別ページ `https://agricola.cloudfree.jp/?p=2991`、英語一覧
  `https://agricola.cloudfree.jp/cardlist_en/`。原文は転載しない。
- 位相: 収穫の畑フェイズ。作物の収穫前後どちらでもよく、自分の畑の収穫内容に依存しない。
- 必要な状態: `Continuation::Harvest` の畑フェイズ、現在プレイヤー、残りプレイヤー、
  各プレイヤーの効果位置。支払い後の木材・食料・台帳。
- 決定: 任意の yes/no。木材1と食料1が無ければ決定を出さない。1収穫につき1回
  （`use_limit: Some(1)`）。複数回使えるかは §5 H3-1。
- 実装手順:
  1. G1 の収穫トランザクションを入れる。
  2. `dispatch_harvest_field` に C098 の専用ブロックを追加し、`Transition::Paused` を返す。
     汎用スキャンは `effect_condition_holds` で false にして二重発火を防ぐ。
  3. `PendingKind::Custom` で `{kind: "c098_exchange", wood: 1, food: 1, points: 1}` を出し、
     `PendingResolution::Custom { confirmed }` で受ける。型付きにするなら
     `PayForBonus` を追加する。
  4. 正本・legacy・dispatcher の3経路で同じ台帳・供給・使用回数になることをテストする。
- テスト: 収穫4/7/9/11/13/14 の各畑フェイズ、木材/食料の不足、拒否、保存→復元→再開、
  同一収穫での二重使用拒否、固定シード再演、台帳の改竄拒否。
- 完了条件: 収穫の途中で C098 の判断が入り、拒否すれば何も変わらず、承諾すれば
  木材1・食料1が減って台帳が1点増え、給餌・繁殖まで到達する。

### C099 ガーデンデザイナー

- 効果（要約）: 得点計算の開始時に、空き畑へ好きな数の食料を置ける。1/4/7 の食料を
  置いた畑1つにつき 1/2/3 点。
- 典拠: `https://agricola.cloudfree.jp/?p=2990`、英語一覧。
- 位相: 得点計算の開始時。最終収穫と帰宅フェイズの後。
- 必要な状態: 空き畑の一覧（農場セル、およびカード畑を含めるならそのID）、食料在庫、
  プレイヤーごとの `ScoringPlan`。
- 決定: 各空き畑に 0/1/4/7 を割り当てる。合計は食料以下。1/4/7 以外の数は点にならない
  ため、合法手からは除外する（2/3/5/6 を許すかは §5 H3-4）。
- 実装手順:
  1. `ScoringPlan` と `score_with_cards_and_plans` を追加する。
  2. 得点フェイズのループ（人間/AI）を追加する。エンジン内 phase か、Web/CLI の
     得点前プロンプトかは設計判断。最低でも plan を保存・再演できること。
  3. 空き畑の列挙を `Player::fields()` ではなく、作物の無い畑に限定する。
     カード畑を含める場合は第2部のカード畑状態を使う。
  4. `card_bonus` に加算し、`cards`（印刷点）は変えない。
- テスト: 空き畑0/1/2/3、食料0/1/4/7/8/14、複数畑への配分、カード畑の有無、
  plan の合計超過拒否、1/4/7 以外の拒否、得点の内訳、固定シード再演。
- 完了条件: 同じ盤面・同じ plan から常に同じ得点になり、plan が保存・再演できる。
  人間が選べる UI があり、AI は最適 plan を列挙できる。

### D099 土器作り

- 効果（要約）: ラウンド4までに出していれば、最後の収穫の後に、人物1人につきレンガ1を
  払ってボーナス1点を得てもよい。最大で人物の数まで。
- 典拠: `https://agricola.cloudfree.jp/?p=2822`、英語一覧。
- 位相: 最終収穫（ラウンド14）の後、得点計算の前。E099 の「収穫終了」と同じ地点。
- 必要な状態: プレイ時ラウンド（1〜4）、家族数、レンガ在庫、台帳。
- 決定: 0〜家族人の整数。1点につきレンガ1。部分支払い（1人だけ）も可。
- 実装手順:
  1. `Player.card_play_rounds: BTreeMap<String, u8>` を追加し、`cards::play` の3経路で
     記録する。`serde(default, skip_serializing_if = "BTreeMap::is_empty")` で旧セーブを読む。
     空の旧セーブは「D099 を出していない」と解釈でき、安全。
  2. G2 の最終収穫後フェイズで `PendingKind::Custom { kind: "d099_clay_for_points", max }`
     を出す。`PendingResolution::Custom { amount }` で受ける。
  3. レンガを引き、台帳へ `D099` として加点する。`finished` は解決後に立てる。
  4. 3経路（正本・legacy・dispatcher）で同じ台帳になることをテストする。
- テスト: ラウンド1/4/5でプレイ、家族2/3/4/5、レンガ0/1/家族数/超過、0点選択、
  保存→復元→再開、最終収穫後の順序、固定シード再演。
- 完了条件: ラウンド4以前のプレイだけが対象になり、最終収穫後に0〜家族人の
  支払いができ、得点計算に反映される。

### A100 後見人

- 効果（要約）: 各ラウンドの帰宅フェイズに、自分の人物3人以上を累積スペースから
  戻したなら、食料1でボーナス1点を買える（1ラウンド1回）。
- 典拠: `https://agricola.cloudfree.jp/?p=3325`、英語一覧。英語の単一条件文と
  リポジトリ内 `data/bga-card-specs/A100.json` の `frequency: every_round` が一致。
- 位相: 各ラウンドの帰宅フェイズ。労働フェイズ（収穫を含む）の後、次ラウンドの
  準備前。ラウンド14では得点計算の前。
- 必要な状態: そのラウンドに各プレイヤーが使ったスペース、累積スペースの判定、
  食料在庫、台帳、1ラウンド1回の使用回数。
- 決定: 任意の yes/no。食料1が無ければ決定を出さない。
- 実装手順:
  1. G4 の `end_round()` を追加し、`start_round` の前に呼ぶ。ラウンド14では
     `finished` の前に呼ぶ。
  2. 使用スペース履歴を §2 G4 の方式 B（`round_placements`）で持つ。
     `Observation` には「帰宅フェイズの自分/他者の累積スペース使用人数」を公開情報として出す。
  3. `is_accumulation_space()` を追加し、動物市場を含める。カード作の累積スペースは §5 H3-2。
  4. `PendingKind::Custom { kind: "a100_food_for_point" }` を出し、承諾なら食料1・台帳1点。
     `use_limit: Some(1)` で1ラウンド1回。
  5. `start_round` の `pending` 禁止契約を守るため、`end_round` の中で解決を完結させる。
- テスト: 2/3/4人、累積スペースに3人/2人、動物市場を含む/含まない、食料0/1、
  承諾/拒否、ラウンド14、保存→復元→再開、固定シード再演、1ラウンド1回の拒否。
- 完了条件: 各ラウンドの帰宅フェイズに条件判定と任意支払いが入り、ラウンド14でも
  得点前に解決できる。

## 4. 依存関係と実装順

```
G0 ボーナス台帳の一本化
 ├─ G1 収穫トランザクション
 │   ├─ C098（畑フェイズの任意支払い）
 │   └─ G2 最終収穫後フェイズ
 │       └─ D099（最終収穫後の任意支払い）
 ├─ G3 得点フェイズの意思決定
 │   └─ C099（得点開始時の食料配置）
 └─ G4 帰宅フェイズ＋使用履歴
     └─ A100（帰宅フェイズの任意支払い）
```

- G0 は全カードの前提。G0 が赤のまま4枚を積まない。
- G1 は C098 と D099 の共通前提。先に G1 だけを独立PRにする。
- G2 は G1 の上に載る。D099 は G1 が無くても「最終収穫後に一括で止める」ことは
  可能だが、C098 と同じ停止契約を使う方が安全。
- G3 は G1/G2 と独立。C099 だけを先に進められる。
- G4 は A100 専用。第2部の「他人の手番トリガー」で必要になる使用スペース履歴と
  一部共有できる（相手の使用スペースを見るカード）。ただし A100 は自分の帰宅フェイズ
  なので、まず A100 単独で設計してよい。
- 各基盤は1ブランチ=1PR。カード実装は基盤のマージ後。基盤とカードを同じPRに
  詰めない（レビュー範囲が広がり、停止条件が曖昧になる）。

## 5. 人間確認（文献で確定できない点）

### H3-1 (P2) C098 は1収穫に何回使えるか

- 文献の要約: 「各収穫の畑フェイズで、このカードを使って木材1＋食料1を1点に交換できる」。
  回数の明示が無い。カード効果は通常、発火ごとに1回と読むが、公式カード現物で
  「once per harvest」の有無を確認したい。
- 影響: `use_limit: Some(1)` か `None` か。複数回可なら木材・食料の使い切り方が変わる。
- 質問: 公式カード/FAQ で1収穫1回か、複数回かを確認したい。

### H3-2 (P2) A100 の「累積スペース」に動物市場・カード作スペースを含むか

- 文献の要約: 英語は "accumulation spaces"。公式ルールの用語では、資源が蓄積する
  スペース（動物市場を含む）を指すと読める。カードが作る累積スペースを含むかは
  カード次第で、現時点では未実装。
- 影響: 動物市場に3人置いた場合の A100 の発火。`Space::accumulation()` は動物市場に
  `None` を返すため、専用の判定が必要。
- 質問: 公式ルールの「累積スペース」の定義に動物市場が含まれること、カード作の
  累積スペースを含めるかを確認したい。

### H3-3 (P1) C099 の「空き畑」にカード畑を含むか

- 文献の要約: C099 は「空いている畑」に食料を置く。第2部のカード畑
  （B068/B113/B141/E068/E069）が「畑」に数えるかは、第2部 Q-1 で未確定。
- 影響: カード畑を持つプレイヤーの C099 の点が変わる。C099 を先に実装するなら、
  カード畑を除外する暫定仕様と、後で拡張する互換性の判断が要る。
- 質問: 第2部 Q-1 と同じ。カード畑が得点・カード前提の「畑」に数えるかを確認したい。

### H3-4 (P3) C099 で 2/3/5/6 の食料を置けるか

- 文献の要約: 「1/4/7 がある畑1つにつき 1/2/3 点」。2/3/5/6 は点にならない。
  「好きな数の食料」なので、点にならない数を置くことは許されそうだが、無意味。
- 影響: 合法手の列挙と UI。AI は 1/4/7 だけを候補にすればよい。
- 質問: 公式カード/FAQ で、点にならない数を置けるか（合法手に含めるか）を確認したい。
  含めないなら `ScoringPlan` の検証で拒否する。

### H3-5 (P1) E100 の OR/AND（既存 H-1）と #332 の分離

- 第1部 H-1 のとおり、E100 の「1つ以上」は日英で OR/AND が矛盾する。
- #332 は E099 と E100 を同時に含むため、E100 の決定待ちが台帳のマージを止める。
- 4枚は E100 に依存しない。**台帳（#327）→ 4枚 → E099/E100** の順に分離できるなら、
  H-1 を待たずに4枚を解放できる。分離するか、H-1 を先に決めるかを人間が選ぶ。

## 6. テスト計画（4枚共通）

1. **3経路一致**: 正本（`cards::*`）／legacy（`apply_*_legacy`）／dispatcher
   （`dispatch_*`）で、同じ論理状態から同じ供給・台帳・使用回数・イベントになる。
2. **固定シード再演**: 2/3/4人、各カードの代表ケース。`state_hash` / `integrity_hash` /
   イベント数が一致する。
3. **保存・復元・再開**: 各 PendingDecision の直後で `save_json` → `load_json` →
   `resolve_pending_and_resume`。`state_hash_before` の一致、改竄拒否。
4. **変異テスト**: 支払いを消す、点を2倍にする、使用回数を無視する、条件を反転する。
   各変異が赤になることを確認する。
5. **AI 観測**: 未公開カード・内部 seed を渡さない。台帳・使用履歴・得点 plan は
   公開情報として `Observation` に載せる。`mcts::sample_game` の決定化でも同じ。
6. **UI**: 人間が各判断を選べる。拒否・0点・部分支払いができる。
7. **公式照合**: カード効果は日英 wiki の要約と照合し、原文は保存しない。
   ルール解釈は `docs/rule-decisions.md` に記録する。
