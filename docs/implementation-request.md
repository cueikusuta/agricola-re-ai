# Part 1：実装依頼文

# アグリコラ対戦AI 実装依頼文

実行役（ChatGPT / Codex 等）へ渡す依頼。設計の正本は設計メモ（`アグリコラ対戦AI-設計メモ.md`）。単一ファイルで完結させる場合、設計の正本は「本ファイル Part 2（設計メモ）」とする。GitHub上では独立した設計メモとして配置してよい。この依頼文と設計メモが矛盾したら、勝手に選ばず矛盾を報告すること。まず今回の範囲は M1 のみ。

最重要原則：ルールエンジンの正確性を維持しながら、AIの意思決定部分を自由に交換できる構造にすること。M1では高度なAIやUIを作る必要はなく、実装の正確性を最優先とする。

## プロジェクトの前提

- 目的：ボードゲーム『アグリコラ リバイズド』（2016年改訂版）の対戦AIを作る。ルールの正本はリバイズド版の公式ルールとし、2007年旧版のルール・カード構成（5人戦、E/I/Kデッキ等）と混ぜないこと。別製品『アグリコラ：ファミリーバージョン』のルールとも区別すること。ネット上の資料は旧版のものも多いので、参照時に版を確認すること。
- 段階：M1 2人戦シミュレーター → M2 評価関数AI → M3 MCTS → M4 3〜4人戦と人間対CPUの対戦UI → M5 職業・小改善カードと非公開情報への対応。
- M1の基準は、リバイズド版の手札なし初心者向けバリアントとする。職業・小改善カードは使わない。主要改善は使用する。公式バリアントのスタートプレイヤー用スペースの変更を反映すること。Side Jobは実装しない。追加アクションスペースは設定で切り替えて実装する（詳細は「M1の確定仕様」）。
- AIの目的関数：勝つことが第一、高得点は第二。M3では勝率と得点差を別々に保持し、勝率を優先する辞書式で扱う（単純な加算にしない）。M1のAIはランダムと貪欲のみでよい。
- 構造の必須要件：
  - ルールエンジンと意思決定を分離する。処理は「合法なアクションスペースの列挙 → AIまたは人間による選択 → 細部決定ポリシーによるパラメータ生成 → エンジンによる合法性検証 → 状態更新とログ記録」とする。細部（柵の形・畑の配置・種まきの配分・家畜の配置・改築の詳細）はエンジンに組み込まず、差し替え可能な細部決定ポリシーに置く。M1では単純なヒューリスティクスでよい。
  - 内部状態とAIの観測情報を分離する。未公開ラウンドカードの順序を含む内部状態をAIに見せず、公開情報だけを返す観測APIを用意する。AIが内部シードから未来の情報を得る実装は禁止。
  - 状態は多人数前提で設計する（プレイヤーは人数可変の配列）。カード効果の差し込み口（フック）だけはM1で設計する。

## M1の確定仕様

- **ゲームモード**：M1はリバイズド版の手札なし初心者バリアントを基準とする。Side Jobと2人用追加アクションスペースは別のオプションとして扱い、採否は以下の通り確定している。
- **Side Job**：実装しない。
- **追加アクションスペース**：公式リバイズド版に準拠して実装する。
  - ゲーム設定 `additional_action_space_enabled` でON/OFFを切り替えられるようにする。初期値はOFFとする。
  - M1では2人戦用タイルの4択（林・資材市場・家畜市場・家族増員）に対応する。
  - 4択のうち1つを使用すると、同ラウンドの残り3つも使用不可になる。
  - 林は毎ラウンド木材1が累積し、林以外が選ばれても木材は保持される。
  - 家族増員はラウンド5以降、空き部屋がある場合のみ使用可能。
  - 設定値は対戦開始時に固定し、保存データと対戦ログに記録する。
  - ON/OFF両方の設定で固定シード対戦・ルールテスト・再現性テストを実施する。
  - M1ではUIを作らず、設定ファイルまたは起動引数で切り替える。
- **ワーカーを使わない操作**：通常のワーカー配置アクションと別に、任意タイミングの食料変換・家畜の再配置・資源の廃棄などを扱う仕組みを用意する。実行可能なタイミングと合法性は公式ルールに従う。M1では自動決定でもよいが、将来はAIと人間が選択できる構造にする。
- **初期状態**：各プレイヤーは木の部屋2つ、家族2人で開始する。開始プレイヤーはシード付き乱数で決定し、開始プレイヤーの食料は2、他プレイヤーは3とする。
- **勝敗判定**：最終得点が同点の場合、手元に残った建築資源（木・粘土・葦・石）の合計で順位を決める。それも同数なら同順位とする。テストにも追加する。

## Step 0：実装前の確認（リポジトリもIssueも、ここが終わるまで作らない）

- M1の実装に必要な仕様のうち、開始前の必須確認事項は「実装言語・実行環境」のみとする（速度の見込みと合わせて提案してよい）。これを人間と確定してから Step 1 に進む。
- Side Jobの採否、追加アクションスペースの仕様、初期プレイヤーの決定方法は「M1の確定仕様」で確定済みのため、確認事項には含めない。
- M2以降のAIの強さの目標と評価方法は、M2着手前までに確定すればよい。今回の確認には含めない。
- なお、実装中に出た不明なルールについては、公式ルールの該当箇所を示し、選択肢と影響範囲を添えて人間の判断を待つこと。推測で確定しないこと。

## Step 1：リポジトリ作成

- GitHub にパブリックリポジトリを作成する。名前は `agricola-re-ai`（本人が指定）。使えない場合は勝手に変えず報告する。
- ライセンスは付けない（本人決定）。
- 初期構成：
  - `README.md`：目的と段階（M1〜M5）の概要。
  - `docs/` に設計メモとこの依頼文を置く（設計の正本は設計メモ）。
  - `AGENTS.md` にプロジェクト指示を置く：正本の優先順位、1 Issue = 1ブランチ = 1 PR、ルール解釈に迷ったら判断待ちにして止めること、M1でやらないこと。
  - リポジトリに入れるのは自作コードと自分の言葉の要約まで。ルールブックのPDF、カード画像、カードテキストの丸ごとデータは入れない。
- 下記の11件を Issue として作成し、依存関係を各Issueに明記する。リポジトリのURLとIssue一覧を報告する。

## M1 のゴール

2人戦を全14ラウンド正確にシミュレーションし、ランダムAI同士で完走・得点計算・完全再現できること。

## Issue 分割案（1 Issue = 1ブランチ = 1 PR、各Issueに対応する単体テストを含める）

1. **基盤**：状態表現、5×3農場、シード付き乱数（用途別に分離）、保存・復元（乱数生成器の状態も含む）、初期状態（木の部屋2つ・家族2人、開始プレイヤーはシードで決定し食料は開始プレイヤー2・他3）
2. **合法手・適用処理**：アクションスペースの列挙、細部決定ポリシー、合法性検証、ワーカーを使わない操作（食料変換・家畜の再配置・資源の廃棄）の仕組み
3. **ラウンド進行**：ワーカー配置、ラウンドカード、資源補充、手番管理、追加アクションスペース（設定 `additional_action_space_enabled`、初期値OFF、2人戦用4択）
4. **農場A**：部屋、建築、改築、家族増員
5. **農場B**：畑、耕作、種まき、作物管理
6. **農場C**：柵、牧場、厩、家畜管理
7. **主要改善**：10種類の効果、食料変換、パン焼き
8. **収穫フェーズ**：収穫、給餌、繁殖、物乞い
9. **得点計算**：全カテゴリの集計、最終結果、勝敗判定（同点時は建築資源の合計、それも同数なら同順位）
10. **対戦AI**：ランダムAI、貪欲AI、自己対戦
11. **統合検証**：ログ再現、固定シード100試合、性能測定、統合テスト

依存関係を明記し、可能なもののみ並列実装すること。

## ルールテストの要件

- 固定テストで最低限検証する：家族増員（部屋の条件、最大5人、新生児の行動開始）、スタートプレイヤー（取得条件と次ラウンドへの反映）、複合アクション（処理順序、任意・必須の区別）、部屋・改築（建築条件、必要資源、全室改築）、畑（耕作、種まき、収穫、作物の残量）、柵（形状、閉鎖条件、隣接、15本上限）、厩・家畜（収容能力、異種混在、ペット、繁殖）、主要改善（10種の購入条件、効果、食料変換、得点）、給餌（通常家族2食料、新生児1食料）、物乞い（不足時の処理、1枚−3点）、最終得点（全カテゴリ、減点、上限、カード点）、勝敗判定（同点時は建築資源の合計、それも同数なら同順位）、追加アクションスペース（設定ON/OFFの両方、4択の排他、林の累積と保持、家族増員の条件）。
- すべての状態更新後に不変条件を検査する仕組みを入れる：資源数が負にならない、農場15マスに不正な重複がない、使用済みアクションスペースを再使用できない、家族・柵・厩の個数上限を守る、家畜の配置と収容数に矛盾がない。
- 固定テストに加え、ランダムな合法手を繰り返すテストも実施する。
- テストは各機能のPRに含める。最後にまとめて実装しない。

## ログと再現の要件

- ログに記録する：ルールバージョンとゲームモード、初期状態・開始プレイヤー、ラウンドカード用乱数シード、AIの行動選択用乱数シード、全アクションと細部の選択内容、各アクション前後の状態ハッシュ、ログ形式とエンジンのバージョン。
- 同一の初期条件とアクション列から、AIの判断を再実行しなくても同一のゲーム状態を復元できること。

## M1 の受け入れ条件

以下をすべて満たすこと。

- 固定シード100試合が全14ラウンド完走する。
- 全試合で合法手と状態の不変条件が維持される。
- 同一シード・同一アクション列から状態ハッシュが完全一致する。
- 中間状態の保存・復元によって同一の結果に到達できる。
- ルールテストが全件成功する。
- 最終得点とカテゴリ別の内訳が出力される。
- ランダムAIと貪欲AIが正常に動作する。
- 1試合あたりの平均実行時間とスコア分布を報告する。
- AIの入力から未公開情報が除外されている。
- 細部決定ポリシーを交換できる。
- 追加アクションスペース設定のON/OFF両方で、固定シード対戦・ルールテスト・再現性テストが通る。
- 不明なルール解釈は未解決事項として報告する。

なお、ランダムAIの平均スコアを人間の平均スコアと直接比較して合否判定しない。正確性はルール照合とテストで、安定性と速度は完走・再現性・実行時間で、AIの強さはM2以降の対戦勝率で、それぞれ判断する。人間のスコア分布は異常検知の補助としてのみ用いる。

## M1 でやらないこと

- 職業・小改善カードの実装。ただしカード効果のフックだけは設計する。
- 3人以上の対戦。ただし状態設計は多人数前提にする。
- MCTS、高度な評価関数。
- 画面のあるUI。対戦ログはテキストでよい。
- 定石ライブラリ（M1〜M3では必須にしない）。

## 進め方

- ルールの正本はリバイズド版の公式ルール。解釈に迷う点が出たら、勝手に決めず、Issue に公式ルールの該当箇所・選択肢・影響範囲を書いて止める（判断は人間が行う）。
- 参考資料：先行実装 jack-and-rozz/agricola（改訂版の状態表現の例がある。家畜管理など未完部分があるので流用は部分的に。また、同リポジトリはルールPDFを含んでいるが、本プロジェクトのリポジトリには入れないこと）、Rust製アグリコラAIの記事 https://hsaikia.github.io/agricola-ai/（分割アクションの扱いと探索量の実績）。
- PR には、実装内容、テスト結果、ルール解釈で迷った点の一覧を書く。
- CI（GitHub Actions）でルールテストと統合テストを自動実行する。パブリックリポジトリのため無料枠で足りる想定。
- 人間が判断したルール解釈は、判断内容と根拠を `docs/` の解釈記録に残す。後から「なぜこう実装したか」を追えるようにする。
- 設計メモと違う進め方が良いと考える場合は、先に理由を挙げて提案してよい。採用するかどうかは人間が判断する。
