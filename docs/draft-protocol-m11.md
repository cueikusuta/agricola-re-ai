# M11 ドラフト詳細設計（Issue #104、独立レビュー案）

初版: 2026-11-06。一次資料照合: 2026-11-08。対象: 2〜4人、職業と小進歩。基本設計・未決定事項を含む文書であり、末尾に実装済み機能・検証範囲を追記している。**各ドラフト方式の既定採用は未決定**。

## 1. 典拠と分類

- **基本ルールと公式付録を区別**: 通常のゲーム開始は職業7枚・小進歩7枚の配布（[Lookout Revised Rules p.11](https://www.lookout-spiele.de/upload/en_agricolare.html_Rules_Agricola-RE_EN.pdf)）。一方、出版社による[2016 Appendix §7「Variants」pp.8–9](https://lookout-spiele.de/upload/en_agricolare.html_Appendix_Agricola-RE_EN.pdf#page=8) は、普及した**選択的な変則ルールの例**として、①play-agricola.com方式の「職業7枚を各1枚取って左回し→同じ操作を小進歩にも行う7-7」、②Agricola app方式の「職業1＋小進歩1を同時に選び、残りを左回し」、③10枚から7枚を選ぶ非パス方式を紹介している。これらは基本ルールの唯一の必須手順ではない。
- **採用判断が必要な方式**: 公式付録記載の7-7左回し方式・app同時ピック方式のどちらを採用するか、10-7の**パス式ドラフト（公式付録には具体手順の記載なし）**、独自の逆回し・左右非対称、タイムアウト処理、2〜4人戦の例外。変則ルールの紹介は既定採用の強制ではない。名称だけから推測せず、採用時は `ruleset_id` と各パラメータを表示する（#155）。
- **プロジェクト固有の提案**: 以下の確定的な状態機械、観測履歴、API、検証ゲート。これらは実装設計案であり、外部の公式手順とは主張しない。

## 2. モード定義

| mode_id | 配布（各人） | 選択 | 受け渡し | 最終手札（各人） |
|---|---|---|---|---|
| `deal_7` | 職業7 + 小進歩7 | なし | なし | 7 + 7 |
| `draft_7_7` | 職業7 + 小進歩7 | 各種別7ラウンド、各回1枚 | 各ラウンド末、未選択の束を隣へ | 7 + 7 |
| `draft_10_7_simultaneous` | 職業10 + 小進歩10 | 各ラウンド**両種別を同時に**各1枚、7ラウンド | 両種別の束をそれぞれ規定方向に回す。**全員の選択確定後**一括移送 | 7 + 7（各束3枚破棄） |
| `choose_10_7` | 職業10 + 小進歩10 | 自分の候補から種別ごとに7枚を選ぶ | なし | 7 + 7（各3枚破棄） |

全モードで開始時のカード抽選は「配布対象の候補プールから、同一カードは全プレイヤーで一度しか配らない」。配布要求数は `7*N` または `10*N` を職業/小進歩**別々**に検証する。複合種別カードは公式照合・専用制約が整うまで抽選対象から除外。4人10-7は各種別40枚の**4人適格・効果検証済み**カードを最低要件とする（Issue #105、#115）。

## 3. ドラフト手順と画面状態

- `setup` → `dealing` → `drafting`/`choosing` → `finalize` → `playing`。
- `draft_7_7`: `phase=occupation` の7回選択完了後、`phase=minor` の7回。職業→小進歩・左回しは公式Appendix p.8のplay-agricola.com紹介例に沿うが、**本プロジェクトでの採用は#155の未決定事項**。逆順・同時進行を許す場合は別 `ruleset_id` とし、同一モード内で無言変更しない。公式付録のapp方式（職業＋小進歩を各ピックで同時選択）とも混同しない。
- `draft_10_7_simultaneous`: `phase=both`、7ピック。プレイヤーは各ピックで職業1＋小進歩1をまとめて送る。束が移動するのは全プレイヤーのコミットが揃った後だけ。未入力・重複コミット・時間超過はエラー/明示再試行。AIの10秒制限は**職業・小進歩を選ぶ一回のピック単位**。
- `choose_10_7`: 各人が自分の職業10中7、小進歩10中7を一括選択。選択順には戦略的効果なし。すべて確定してからゲームへ。3枚ずつの未選択カードは `discarded_private` として内部管理し、公開しない。
- `packet_id` と `owner_seat` を区別し、各ラウンドでパケットが席順方向に1席移動する。 `direction_occupation`、`direction_minor` は `left/right` の明示設定。2人戦でも明示記録。公式Appendix p.8で紹介された7-7方式では職業・小進歩とも**left**だが、左右非対称・逆方向とする別慣行の典拠は**未確認**。
- パス方向、開始プレイヤー基準のピック順（同時/順次）、2人戦・3人戦での採用可否、ドラフト中の時間切れ方針を **open rule decision** として残す。未決定時は開始を拒否し、恣意的な既定方向にしない。

### 数量・保存不変条件
- 選択済み手札 + 未選択パケット + 未配布 + 破棄 = 開始時カード集合。カードID重複0。
- `draft_7_7`: 各種別の各ラウンドで束サイズは7,6,…,1。7ラウンド後、各人選択済み7、残束0。
- `draft_10_7_simultaneous`: 束サイズは10,9,…,4。7ラウンド後、各人7枚＋残束3枚、全パケット残束を破棄領域へ。
- `choose_10_7`: 初期10→選択7/破棄3。
- カード効果はゲーム中の公開済みカード以外は発動しない。選択中のピックから対戦処理を開始できない。

## 4. 観測モデルと非公開情報

権威状態 `DraftState`（非公開）と `DraftObservation{viewer, ruleset_id, phase, round, offered_ids, own_picked_ids, own_observation_history, public_picks, hand_counts, remaining_to_pick, request_token}` を**別型**にする。 `DraftObservation` は観測者が正当に知ったカードと公開枚数のみを含み、内部seed・デッキ順・他人の候補束の全容・他人の最終手札をシリアライズしない。

- `own_observation_history` は時系列の `SeenPacket{round,kind,ids,source_packet_id}`、`OwnPick{round,kind,id}`、`PassedPacket{round,kind,ids}`、`PublicReveal{event_id,player,id}` を保持（プレイヤーごとにイベント投影）。
- 一度見たが既に手元にないカードも履歴に残る。**自分が以前見た束から相手が取ったカードは、今の手札の直接情報として出さず**、AIが観測履歴と合法なルールから推論する。
- 公開イベントのみ全員へ。相手の隠し手札、現在のパケット実体、未公開のラウンド順、内部seedはAI用構造体・UI応答・探索用の観測に含まれない。
- 将来の多人数Webでは `viewer` をHTTPクエリで自由指定させない。**サーバ側の認証/セッションで観測者を決定**する。現行 `src/web.rs` はローカル単一人間向けで `hand[0]` と `seed` を返すため、現行状態JSONをそのままAI/マルチユーザ公開APIへ流用しない。
- AIシミュレーションの隠れ状態サンプルは、公開情報・自分の履歴に整合する候補集合からのみ生成。正解の内部デッキ/相手手札/seedを参照するAPIを持たせない。

## 5. 保存・再演・監査

`DraftState` に `schema_version`, `ruleset_id`, `private_seed_or_rng_state`（権威サーバー状態にのみ保存しAI/他人への観測では絶対に出さない）, `seed_commitment`（公開が許された場合のみ）, `deck_version`, `engine_sha`, `player_count`, `round`, `phase`, `packets`, `picked`, `discarded_private`, `commitments`, `event_index` を保持。既存セーブと区別したバージョン化。ゲーム実行ログには各選択イベントを決定的に記録し、ハッシュは**秘匿を保ったサーバ側の完全ログ**と、必要なら公開観測ログを別々に算出する。

復元直後・イベント再演後に不変条件、最終配布、各人の観測履歴、公開情報、再演ハッシュが一致。未入力のコミットも保存するが他人へ明かさない。再接続とサーバプロセス再起動からの復元は**別試験**。

## 6. API契約案（正式エンドポイント名は既存web API整合確認後）

| 操作 | 入力 | 出力 | 不正時 |
|---|---|---|---|
| `create_draft` | mode, ruleset_id, player_count, eligible_deck_version, seed（信頼されたサーバのみ） | draft_id, phase, public status | 422: 未確定ルール/人数/枚数不足 |
| `observe_draft` | セッション認証（viewer はサーバ決定） | `DraftObservation` のみ | 403: 権限外 |
| `commit_pick` | draft_id, request_token, phase, round, selected card ID（同時なら職業＋小進歩） | accepted, next observation, event index | 409: 古いターン、422: 候補外/種別/重複/枚数違い |
| `confirm_choice_10_7` | 各種別7 IDs, request_token | accepted | 422: 重複/配布外/枚数不足 |
| `resume_draft` | 保存ID, session | 観測者ごとの投影 | ハッシュ・版の不一致は拒否 |

`request_token` は一度きり/冪等キーを併用し、通信再送による二重ピックを防止。失敗時は原子性を維持して状態・履歴・ハッシュを変えない。結果が揃った時にのみターンを進める。AIの合法候補は `offered_ids` から生成し、サーバで最終チェックする。

## 7. テスト・UI受入

1. 人数2/3/4 × 4モード × 職業/小進歩の各枚数、不足・重複・人数不適合・複合種別除外。
2. 全ラウンドのパケット所有者と通過方向、2人時の折返し、3人時の循環、両種別逆方向の設定を固定seedで確認。
3. 全員コミット前にパケットを移送しない、同一要求の再送・古いトークン・他人のカード指定を拒否。
4. 同一seed・版・全選択列で完全再現。選択途中の保存/復帰・プロセス再起動・ハッシュ同一。
5. **非干渉テスト**: 観測者に見えていない他人の手札/内部seedだけが異なる2状態で、観測APIの出力が同じであること。隠しイベントを別APIに誤って入れない。
6. UI Playwright：日本語カード名と自作概要、選択数、残り枚数、パス先表示、別プレイヤー視点の秘匿、通信再送、途中再開、全ピック→ゲーム開始。APIテストと別ゲート。
7. AI：同じ観測だけで合法ピック、同条件で固定seed再現、全4モードで14ラウンド完走（M10検証済みプールが揃ってから）。1ピック10秒を実測、合法候補へフォールバック。

## 9. 実装状況（2026-11-07、Task A / #104）

- `src/draft.rs` に `DraftCardInfo`、`DraftObservation::catalog`、`observe_with_catalog` を追加。カタログは `Observation::card_definitions` と同じ公開語彙のみで、未実装の効果を推測してはならない。
- `src/draft_game.rs` が確定ドラフトとゲームを接続する唯一の入口。`hands_from_completed_draft` と `start_game_from_draft` は未完了ドラフト・不明カード・人数不一致を拒否し、`Game::with_cards_and_hands` が通常のランダム再配布を回避する。
- `GameLog.initial_hands` に初期手札を保存し、`Game::replay_with_setup` と `load_json` が同じ初期状態を再構築する。`Game::with_cards` の通常配布は従来どおり（`initial_hands = None`）。
- 本番プールは `verified_basic`（現状は2人・通常7枚/7-7のみ。10-7は枚数不足で拒否）。統合検証は `test_fixture`。フィクスチャID `FIX-*` は `verified_*` に登録しない。
- ブラウザは `POST /api/draft/start-game` でドラフト完了後にゲームを開始し、観測履歴はセッションに保持する。相手の最終手札は開始後も `DraftObservation` に出さない。
- ドラフトAIは `src/draft_ai.rs` の Random / CardValue / Synergy の3種。すべて `DraftObservation` のみを入力とし、公開カタログ（宣言点数・宣言費用・実装済み効果タグ）だけを評価に使う。カタログ欠落時は合法手へフォールバックする。固定seed・座席交代の比較は `compare_draft_ais`。公式照合済みプールが不足するため、**実戦の強さは未評価**（機能検証のみ）。
## 10. ブラウザE2Eで確認した範囲（2026-11-08、Issue #104・#155）

`tests/e2e/draft-verified.test.cjs`（`npm run test:e2e` に含まれ、`web-e2e.yml` で実行）は、
描画済みのボタンとフォームだけで操作する。`state.draft` は局面判定と「サーバが何を返したか」の観察にのみ使い、
`fetch` による直接操作は行わない。

- **実装済みプールの7-7**：明示設定（職業left・小進歩right・職業先行・2人）で開始し、14回のピックをUIで完了、
  自分の最終手札7+7を確認、`この手札でゲーム開始` から通常のゲームに入り、手札がドラフト結果と一致し、
  相手手札が非公開のまま盤面操作できることを確認する。
- **供給不足の明示拒否**：`verified_basic` で10-7同時ドラフト（職業20枚必要）と4人ドラフトは拒否され、
  理由（`occupation pool has 14 cards but ... needs 20` / `two players only`）が画面に出て、
  実行中セッションの観測内容が変化しないことを確認する。
- **明示設定の可視化**：`draft_json` に `player_count`・`direction_occupation`・`direction_minor`・
  `occupation_phase_first` を公開パラメータとして追加し、画面の状態行に「人数／受渡方向／順序／ルールセットID」を表示する。
  方向・フェーズ順は未確定の対戦慣行（#155）であり、**既定値を推測せず、選んだ値をそのまま表示する**だけにした。
- **途中保存・復帰**：4ラウンド分ピックした後 `page.reload()` し、`phase`・`round`・`active_kind`・
  `own_picked`・提示札・`history`・`hand_counts`・`request_token` が完全一致することを確認。
  その後ピックを再開して完了できることまで確認する（サーバープロセス再起動をまたぐ復元は別試験のまま）。
- **観測履歴**：`#draftHistoryEntries` に「見た束」「自分の選択」「渡した束」が出ること、
  非公開情報のキー（`seed` / `packets` / `discarded_private` / `final_hands` など）が
  ブラウザ向け観測JSONに存在しないことをキー集合で確認する。
- **ドラフトAI 3種**：`random` / `card_value` / `synergy` を選択でき、`state.draft.ai` と画面表示に反映されること、
  通常配布（`deal_7`）で各AIが7+7を確定できることを確認する。

**未確認のまま残す**：パス方向・フェーズ順の公式採用（#155）、4人・10-7に必要な公式照合済みカード40+40（#105/#115）、
ドラフトAIの実戦強さ（公式照合済みプール不足）、サーバープロセス再起動からの復元、複数人間セッションの認証。
