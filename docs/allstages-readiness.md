## 第0章 枠組み

### 0.1 段階の定義と、#355 / #360 からの番号の付け替え

本PRで使う段階は、設計判断で確定した次の4段階である。

| 段階 | 定義 |
|---|---|
| 段階1 | OR 費用のカード（支払い束の選択） |
| 段階2 | 他人の手番で発動するカード、畑になるカード |
| 段階3 | 帰宅フェイズと部屋に関わるカード |
| 段階4 | 異種の効果が積み重なるカード |

**#355 / #360 との相違（報告）**: 先行2文書は「段階1 = OR費用＋他人手番＋カードスペース（59枚）」
「段階2 = カード畑（5枚）」という番号を使っていた。今回の設計判断では
「段階1 = OR費用のみ」「段階2 = 他人手番＋畑」なので、**番号が1つずれる**。対応は次のとおり。

| 本PR | #355 / #360 | 枚数 |
|---|---|---:|
| 段階1 | 段階1-A（OR費用） | 13 |
| 段階2 | 段階1-B（他人手番42＋カードスペース4）＋段階2（カード畑5） | 51 |
| 段階3 | （先行文書になし。帰宅・部屋は一部が段階2のカード内に混在） | 65 |
| 段階4 | （先行文書になし） | 95 |

以後の章・PR・Issue では本PRの番号を使う。先行文書を参照するときは「#355 の段階1-B」のように
旧番号を明記する。**分類の実体（どのカードがどの基盤を要求するか）は変えていない**ので、
#355 / #360 のカード別記述はそのまま再利用できる。

**#360 との範囲差（補完）**: #360 の対象は60枚（OR13＋他人手番42＋カード畑5）で、
カードスペース型4枚（A039 / B042 / C162 / D051）は「#355 §2.5 の別枠」として外していた。
本PRでは段階2の定義に「他人の手番で発動するカード」を含むため、この4枚を段階2に入れて
実装準備を補完する（第2章）。

### 0.3 割り当て規則（重なりと区分の取り違えの処理）

各カードは次の順で判定し、**最初に該当した段階**に1つだけ割り当てる。

1. 実装済み → 対象外（実装済み）
2. **段階1**: 費用が「A または B」の支払い束になっている。
3. **段階2**: 他人の手番に発動する／カードが全員用アクションスペースになる／カードが畑になる。
4. **段階3**: 帰宅フェイズに発動・条件がある／部屋（建設・数・種類・収容・得点）または
   住居スロット（人物1人分の住む場所）が効果の条件・対象・発生源になっている。
5. **段階4**: 異なる発動サイト（出したとき／反復トリガー／常時・いつでも／終了時得点）を
   2つ以上またぐ、または1つのサイトで3操作系以上が重なる（第4章の判定規則）。
6. 上記に該当しない → **段階外**（単一サイト・単一操作で、4段階のどの基盤にも依存しない）。

この順序の意味は「**早い段階の基盤だけで実装を始められるカードを先に確定する**」ことである。
段階3に部屋の要素と積層の要素が両方あるカード（例: B136 執事）は、部屋の基盤を必要とするため
段階3に置き、積層の側面をそのカードの「残件」に記録する。段階2のカードが部屋や積層を
併せ持つ場合も同じ扱いで、段階2に置く。

**重なりの記録**: 段階1〜3のカードが段階4の条件も満たす場合は「重なり」として各章の
残件欄に記し、段階4の枚数には二重計上しない。段階4の95枚は「段階1〜3のいずれにも
該当しなかった積層カード」である。

**段階外の扱い**: 段階外は「実装しない」という意味ではない。単一サイト・単一操作で
4段階の基盤を必要としないため、通常のカード実装PR（`data/bga-card-specs` と
`docs/bga-card-effect-vocabulary.md` の語彙で個別に実装）で進められるカードである。
第1章の表には、どのサイト・操作の組み合わせか（仕様JSONの `trigger` / `operation`）を残した。
仕様JSONが空のカードは効果文から区分した。

### 0.4 記号

#360 §0.2 の記号を継承し、段階3・段階4で使う記号を足す。

| 記号 | 内容 |
|---|---|
| **PS** | 公開状態の単一正本（PublicState 集約）。カード上資源・カード畑・使用済み・累積・マーカー・スキップ・一発フラグを公開状態に置き、Observation へ射影する |
| **TR-SITE** | イベントサイト軸（EventKind＋payload）。「何が起きたか」を型で表す |
| **TR-PHASE** | 解決フェーズ軸（Before / After / Interrupt と所有者範囲 `other` / `all`） |
| **SC** | 走査範囲の段階化（アクター本人 → `other` → `all` → `Before`） |
| **DEC** | 相手手番中の所有者 PendingDecision（AI 席も同じ経路で解決する） |
| **DEF** | 定義の正本化（費用の選択肢・前提・効果型・能力メタデータ・出典URL） |
| **LOG** | 記録・再演（支払い束・選んだ対象・配置セル・移動・スキップ） |
| **RH** | 帰宅フェイズのサイト（`TR-SITE = ReturnHome`）。戻した人物、使用済みスペース、周回、新生児数、そのラウンドの獲得物を payload に持つ |
| **ROOM** | 部屋サイト（`RoomBuilt` / `RoomCountChanged`）。建てた部屋のセル・数・家の種類、部屋数・空き部屋・住居スロットの問い合わせを含む |
| **STACK** | 積層カードの共通基盤（複数サイトの登録、サイト間の状態受け渡し、解決順） |

`RH` と `ROOM` は新しいイベント種別の提案ではなく、「段階3のカードが要求する payload」の
名前である。実装側の設計（Dispatcher の2軸化）を確定させる指示ではない。

## 第1章 分類の全体確定

### 1.1 点検の方法

1. #355 の分類（段階1-A 13枚、段階1-B 42枚、カードスペース4枚、カード畑5枚、関連4枚）を
   起点に、636枚すべてを台帳と突合した。#355 の分類に無いカードが「漏れ」、複数の分類に
   出てくるカードが「重なり」である。
2. 実装済み40枚を `src/cards.rs` から機械抽出して除外した。
3. 段階1は台帳の `cost_alternative` と効果文を再確認した（13枚の結論は #355 / #360 と一致）。
4. 段階2は #355 の42枚＋4枚＋5枚を再確認し、カードスペース4枚を段階2に統合した。
5. 段階3は636枚の効果文から「帰宅」「部屋」「住む場所（住居スロット）」を全文検索し、
   個別ページで条件・対象・発生源を確認して採否を決めた（第3章）。
6. 段階4は仕様JSONの `effects[].trigger` と `steps[].operation` を機械集計し、
   2サイト以上または3操作以上のカードを候補にしたうえで、効果文で境界を確認した（第4章）。
   仕様JSONが空のカードは効果文から同じ規則を適用した。
7. どの段階にも該当しないカードは、仕様JSONの `(trigger, operation)` の組を根拠に
   「段階外」として区分した（0.3）。

対象636枚のうち、個別ページから効果文を取得できたのは **634枚**。D025 / D159 の2枚は
台帳に個別ページ URL が無く、分類を保留した（#355 Q-9 継続）。

## 第3章 段階3 帰宅フェイズと部屋（65枚）

### 3.1 抽出と内訳

636枚の効果文から「帰宅」「部屋」「住む場所（住居スロット）」を全文検索し、
個別ページで条件・対象・発生源を確認した。段階1・2・実装済みに該当するカードを除いた65枚。

| 群 | 枚数 | 内容 | 主な要求 |
|---|---:|---|---|
| 3a 帰宅フェイズ | 15 | 帰宅フェイズに発動・判定する | **RH**（帰宅サイトと payload） |
| 3b 部屋 | 44 | 部屋の建設・コスト・数・種類・収容・得点 | **ROOM**（部屋サイトと部屋数/住居の問い合わせ） |
| 3c 住居スロット | 6 | 人物1人分の「住む場所」を増減・無視する | **ROOM** の住居スロット |

重なり: 3a のうち A127 と D010 は部屋・住居も使う。3b のうち B136・B021・B092 は
段階4の積層条件も満たすが、部屋・住居の基盤を先に必要とするため段階3に置いた（第1章 §1.4）。

### 3.2 基盤契約（RH と ROOM）

**RH（帰宅フェイズ）** — 帰宅フェイズは「労働フェイズの後に全員の人物を戻す」フェイズで、
収穫のあるラウンドでは収穫の後に来る。カードは次の payload を要求する。

| payload | 使うカード |
|---|---|
| ラウンド番号、収穫の有無 | A053, A058, B139, D018 |
| 戻した人物のスペース（誰がどこから戻したか） | A035（漁）, A152（授業） |
| そのラウンドに得た建設資材の合計 | A053 |
| 使用済みスペースの集合（帰宅開始時点） | A141, C155 |
| 新生児の数・その収穫で戻した新生児 | A035 |
| 部屋数・家族数・住居スロット | A127, D010 |
| 帰宅フェイズの開始／終了の区別 | A029, A141, A151, A157, C155, D010, D018, D052 |

**ROOM（部屋）** — 部屋は「建てた部屋のセル・数・家の種類」と「現在の部屋数・空き部屋・
住居スロット」の2種類の問い合わせを持つ。カードは次の payload を要求する。

| payload | 使うカード |
|---|---|
| 建てた部屋のセル・数（1アクションで複数室） | A014, A021, A123, A167, B087, D123, E127 |
| 建てた部屋の素材（木/レンガ/石）と家の種類 | B111, D123, E049, E168 |
| 現在の部屋数（条件・得点） | B073, B114, B136, C010, C030, C123, C127, D034, E032, E168 |
| 空き部屋（家族が住んでいない部屋） | C021, C024, D021, E168 |
| 住居スロット（部屋＋カード・厩による拡張） | A010, A127, B021, B085, B092, B127, C024, E151 |
| 部屋のコスト・代用・軽減 | A014, A123, B145, C013, C014, C122, C128, D013, D015, D121 |
| 部屋の得点・排他 | C030, C132, D034, E032 |

RH と ROOM は既存の `EventKind` を置き換える提案ではない。`TR-SITE` に
「帰宅」「部屋建設」「部屋数の変化」を足したときに、payload へ何を載せるかを固定する。

### 4.1 定義と抽出方法

段階1〜3のいずれにも該当しないカードから、次のいずれかを満たすものを段階4とした。

5. **共通テスト**: 正常系・境界・不発・保存復元・再演・秘匿・相互作用。固定シードで
   2/3/4人 × 追加スペース OFF/ON の短い再演。
6. **CI**: 通常PRは軽量テスト（60秒以内を目標）。`cargo fmt --check`、clippy、

7. **レビュー**: ゲームルール・状態遷移・公開/非公開・保存復元・AI評価に関わるPRは、
