# ルール解釈記録

実装中に公式ルールと設計の不一致・曖昧さを発見したら、ここに典拠・候補・影響範囲・人間の決定を記録。

- 現状：未判断事項なし（公式ルールの照合は未完了）。

## 2026-11-04 公式付録に基づく確認済み修正

- **畑の得点**：0〜1枚は-1点、2/3/4/5枚以上は1/2/3/4点（Appendix p.11、"Field Tiles"）。初期ドラフトの誤った計算を修正。
- **パン窯**：Clay Ovenは1回のパン焼きにつき穀物ちょうど1→食料5、Stone Ovenは最大2→各4（Appendix p.2、"Major Improvements"）。上限を修正。
- **調理による野菜の食料化**：暖炉は野菜1→食料2、調理場は野菜1→食料3（Appendix p.2）。フリー変換を更新。
- **追加タイル**：4択の1つを選ぶとラウンド中ほか3つも使用不可。林の木材は選ばれなくても保持（Appendix p.8）。

### 追加で公式照合が必要

- パン焼きに複数の改善を同時利用する場合の細部指定を、現在の`bake: u32`から改善ごとの割当へ拡張すること。
- 柵の内部仕切り・牧場の拡張と分割の一般形を実装すること。
- [確認済み] 動物・資源・作物の一般供給は、物理トークンが不足したら代用品を使える。ルール上の有限上限にはしない。

## 2026-11-04 M1追加検証：柵とパン焼き

- **牧場内の分割**：既存牧場を内部柵で分けることは認められる。2016年リバイズド版公式付録 p.7（Fencing）・ルールブック p.8（Animal Husbandry）。完成済みの外周柵を取り壊すことは認められない。`FenceDetailed` は分割後の牧場領域と家畜の配置を明示する。
- **パン焼き時の設備選択**：公式ルールブック p.10・付録 p.2。交換はいつでも自由な「パン焼き」アクションがある時だけ。各Clay Ovenは1粒を食料5、Stone Ovenは最大2粒を各食料4にする。複数設備の選択は新しい `BakeAllocation` で外部ポリシーから明示できるようにする。
- **追加したモデル**：`SowDetailed`・`BuyDetailed`。旧来の整数 `bake` はテスト互換のため残し、決定的な割当を実行する。
- **未解決**：入手した動物をどの牧場に割り当てるかと繁殖後の移動のルール細部、カードフックと収穫ポリシーのログ完全再現性は引き続き受け入れ前の検証対象。


## Issue #27: 大きな進歩の購入方法（2016改訂版）

- 公式付録 p.2「Major Improvements」：全10枚の建築費・得点・工房変換。かまど（Fireplace）を保有していても、調理場（Cooking Hearth）を**建築費で購入**できる。既存のかまどを返却するのは代替手段であり強制ではない。
- 新しい `Detail::BuyWithMode` は `PurchaseMode::Pay` と `PurchaseMode::Exchange(Fireplace2/Fireplace3)` を明示できる。従来の `Detail::Buy` は互換性のため自動交換を継続。
- 2016年版の付録 p.2 は https://www.lookout-spiele.de/upload/en_agricolare.html_Appendix_Agricola-RE_EN.pdf 。カード本文や画像を公開リポジトリへ含めない。

## 2026-11-04 公式ルールブックp.12：一般供給の有限性

- 公式ルールブック末尾の「Number of Components」は、各プレイヤーの**人5、厩4、柵15**だけを意図的な個数上限とし、それ以外の共有トークンが不足した場合はgoods tilesまたは代用品を使用できると明記する。
- よって羊18/猪15/牛13、木30/粘土24等は同梱の物理的なコマの数であり、ゲーム内の獲得数の上限ではない。シミュレーターでは一般供給を有限化しない。Game::validate は個人コマの上限をチェックする。
- 根拠：https://lookout-spiele.de/upload/en_agricolare.html_Rules_Agricola-RE_EN.pdf p.12、Number of Components。

## Issue #45: 厩の設置場所（2016版ルールブック p.8）

- 「Farm Expansion」で新しい厩を建設できるのは、部屋・畑・牧場タイルのない農場マスだけ。すでに牧場になったマスに厩を後付けするのは不可。
- 逆方向（先にタイルのないマスに厩を建て、後からそのマスを柵で囲う）は合法。囲いの中の厩はその牧場の収容能力を倍増する。
- `build_stable` は `Tile::Empty` のみ受け入れ、`build_pastures` は既存の厩を囲う処理を維持する。失敗時の不変性と順序の回帰テストを追加。
- 根拠： https://lookout-spiele.de/upload/en_agricolare.html_Rules_Agricola-RE_EN.pdf p.8。

## 2026-11-08 M8-2 詳細操作API監査（#109）

対象：`Game::validate_action` / `Game::apply` / `Game::apply_free` と `SimpleDetails` の候補集合。
回帰テスト：`tests/m8_detail_api_audit.rs`（18件、`cargo test --test m8_detail_api_audit`）。

- **確認できた受理**：`SimpleDetails` が作らない詳細も、共通検証器が受理することを確認した。柵の複数牧場（1アクションで2牧場）、畑の任意マス・2マス目以降の隣接要求、部分播種と作物混在、2室+厩の同時建設、牧場/厩/ペット/調理/破棄の混在配置、炉→かまどの順の明示パン焼き、かまどを購入費で買う選択、給餌順序の明示、収穫前の作業取消不能性、フリーアクションの変換・調理・破棄・再配置、播種のみ／新規開墾マスへの播種。
- **確認できた拒否**：重複・非連結・重なり牧場、未接続の2枚目畑、種不足・重複播種、厩の部屋マス設置、牧場の異種混在・頭数不一致、設備の重複使用・炉の能力超過、非炉への即時パン焼き、不正な給餌順序、家畜を増やす再配置。いずれも状態ハッシュ・ログ・使用済みスペースを変えない。
- **回帰**：非既定詳細を含む操作列が `save_json`/`load_json` と `Game::replay` で同一ハッシュになることを確認（状態を改変しない自然な対戦列で検証）。

### 未判断（公式資料の確認待ち。推測で仕様を変更しない）

1. **同一アクションでの非隣接な複数牧場**：現在 `build_pastures` は「新規牧場は既存牧場（または同じアクションの他の新規牧場）と辺で隣接すること」を要求する（`src/engine.rs` の "new pastures must be adjacent" / "new pasture is not adjacent to existing pasture"）。1アクションで離れた2つの牧場を作る操作は受理されない。`docs/design.md` の柵テスト項目に「隣接」とあるため、意図的な制約か実装上の都合かを公式ルール本文で確認する必要がある。影響：離れた牧場を作る人間操作がUIで拒否される。確認先：2016年改訂版ルールブック柵の項、付録 Fencing。
2. **部屋数の上限**：`build_room` と `Game::validate` は部屋数の上限を持たず、得点も部屋数に比例する。公式コンポーネントの部屋コマ数が上限なら不変条件の追加が必要。確認先：ルールブック柵・部屋の項、Number of Components。
3. **調理設備なしの野菜→食料**：`FreeAction::ConvertCrop` は調理設備がない場合も野菜1→食料1を許可する。暖炉・調理場の変換率（野菜1→2／3）は確認済みだが、設備なしの可否は未確認。確認先：付録 p.2。

## 2026-11-16 ボーナス点の持ち場（基盤PR: `Game::bonus_points`）

カードがプレイ時・ラウンド開始時・収穫時に得る「ボーナス点」（E098 神童、E101 はみだし者、
E100 博物館の館長など）を、得点計算時に盤面から再計算できないため、どこに保持するかの設計判断。

- **採用**: `Game.bonus_points: BonusPointLedger`（プレイヤーID → 発生元カードID → 累計点）を
  bookkeeping 台帳として持つ。印刷点の合計を表す `Player.card_points`（`CardState::validate_card_points`
  が不変条件を検査）には**加算しない**。`Player` の新フィールドにもしない（`Player` は
  `PublicState` の中にあり、`LOG_VERSION=5` の `Game::state_hash` タプルに含まれるため、
  追加すると既存の記録ハッシュと `tests/fixtures/v5/*` がすべて変わる）。
- **永続化と整合性**: `state_hash` の7フィールドタプルは変更しない。台帳は `integrity_hash`
  にのみ含め、空のときは旧タプルとバイト一致させて旧ビルドが発行したセーブの検証を通す
  （`serde(skip_serializing_if)` により空台帳は保存JSONにも現れない）。
- **公開情報**: カードのプレイとその効果は公開情報なので、`Observation.bonus_points` に
  公開ミラーを持つ（未公開の手札・内部seedは含めない）。MCTSの `sample_game` もこのミラーを
  引き継ぐ。
- **得点への反映**: `score_with_cards_and_bonus` / `standings_with_cards_and_bonus` /
  `Game::standings()` で `card_bonus` カテゴリに合算する。カテゴリ集合は従来と同一。
- **検証**: `Game::validate` は「実在するプレイヤー」「そのプレイヤーが実際にプレイしたカード」
  「1〜`MAX_STORED_BONUS_PER_CARD` 点」を検査する。
- **残る制約（後続章で解消）**: 得点計算・順位計算は本PRで台帳を読むが、AIの評価関数
  (`evaluation.rs`) は現時点で台帳を読まない。カード効果語彙（dispatcher/正本/legacy の
  各経路）は次章のカード実装PRで追加する。

## 2026-11-17 E099 無関心な親 / E100 博物館の館長の解釈と収穫終了イベント

- **E099 無関心な親**「各収穫の終わりに石の家に住んでいるならば、ボーナス1点」
  → 収穫の3フェイズ（畑→給餌→繁殖）がすべて終わり、まだ次のラウンドが始まっていない時点を
  「収穫の終わり」とする。`harvest()` の繁殖適用後に `dispatch_harvest_end` を呼ぶ。
  条件は家の素材のみ（石の家だけ）。獲得点は台帳（`Game::bonus_points`）に記録し、
  印刷点 `Player.card_points` には加算しない。
- **E100 博物館の館長**「各労働フェイズのはじめに、木・レンガ・葦・石・小麦・野菜のいずれかが
  ストックにあればボーナス1点」
  → 「労働フェイズのはじめ」＝準備フェイズ（累積資材の配置）終了直後・最初の人物配置前。
  `Game::start_round` はラウンド番号更新・ラウンドカード公開・累積資材の加算・遅延食料の配布を
  終えてからラウンド開始トリガーを dispatch するため、既存のラウンド開始地点がそのまま使える。
  対象は6資材のみで、食料と家畜は数えない。
- **イベント地点の分離**: `cards::BonusEventSite` { StartRound, HarvestEnd } を導入し、
  点数計算 `cards::event_bonus_points(site, effect, player)` が site 込みで判定する。
  あるカードの点が別のイベントで支給されることはない（テストで相互漏れを確認）。
- **実装位置**: 台帳は `Player` に無いため、汎用ハンドラではなく dispatcher の専用ブロックが
  `cards::store_event_bonus_points` を呼ぶ。汎用スキャンは `effect_condition_holds` が false を
  返すので二重支給しない。イベント予算1単位とカード使用上限は通常効果と同じく消費する。
- **予算の扱い**: 収穫終了は畑フェイズと同じく独立した効果チェーンなので、開始時に
  イベント予算をリセットする。`integrity_hash` は残予算を含むため、カード有り固定対戦の
  最終 `integrity_hash` が1件だけ変化した（`state_hash`・初期ハッシュ・カード無し対戦は不変）。
- 典拠: BGAアグリコラカード情報wiki 個別ページ（E099 `?p=2654`、E100 `?p=2653`）と
  カード一覧 `https://agricola.cloudfree.jp/cardlist/`。原文は転載しない。
- **未確定（人間の決定待ち）**: A100 後見人の「累積スペースから人物3人以上を戻すたびに」が
  ラウンド1回なのか3人ごとに繰り返すのか。リポジトリ内 spec `data/bga-card-specs/A100.json` は
  frequency=every_round（ラウンド1回）としている。実装前に確定させる。
  → **第3章（2026-11-17）で解消**: 英語のカード一覧（`https://agricola.cloudfree.jp/cardlist_en/`）が
  「3人以上を戻したなら食料1で1点を買える」という単一条件文で、`every_round` と一致した。

## 2026-11-17 ボーナス点カード残り4枚の実装停止（第3章）

対象: C098 サイコロ彫り / C099 ガーデンデザイナー / D099 土器作り / A100 後見人。
結論: **4枚とも実装しない**。`Game::bonus_points`（台帳）は既にあるが、4枚に足りないのは
台帳ではなく「いつ・誰が・何を払うかを決める」意思決定と「過去のラウンドを覚える」記録である。

- **部分実装はしない**。C098 の「出したときに木材1」だけを入れれば通るが、本体の任意交換が
  無いカードがプールに入ると対戦結果がルールと食い違う。「完全に実装」か「理由付き保留」の
  二択を維持する（章1・章2と同じ基準）。
- 各カードの不足基盤（実コードで確認した根拠）:
  - C098: 収穫途中の任意交換。`Game::harvest` は畑→給餌→繁殖を一気に解決し、給餌・繁殖は
    引数の計画を適用するだけ（`src/harvest.rs:165`）。`pending::Continuation` は post-work
    チェーンのみ（`src/pending.rs:96`）、`ChainStep` は3種のみ（`src/pending.rs:52`）。
    加えて `dispatch_harvest_field` は `Transition::Paused` を返しうるが、呼び出し側
    `harvest_fields` は `.expect(...)` で遷移を捨てて収穫を続ける（`src/harvest.rs:125`）。
    現存カードに畑フェイズの中断効果が無いので実害は無いが、C098 が最初の該当例になるため、
    「Paused を黙って捨てない」契約（Issue #268 R2-P0-2 の方式）へ揃えるのが前提。
  - C099: 得点フェイズの意思決定。`score()` は `&Player` だけを受ける純関数（`src/score.rs:35`）。
  - D099: プレイ時ラウンドの記録（`Player.played_cards` は `Vec<String>` でラウンドを持たない、
    `src/model.rs:185`）と、収穫終了時の任意支払い（`dispatch_harvest_end` は
    `BonusEventSite::HarvestEnd` の決定的付与専用で、フェイズ解決も中断も持たない、
    `src/card_events.rs:1629`）。
  - A100: 帰宅フェイズの dispatch 地点が無い（`src/card_events.rs` の `pub fn dispatch_` は7地点）。
    「誰がどのスペースへ置いたか」の記録も無い（`PublicState` は `used: BTreeSet<Space>` のみ、
    `src/model.rs:533`）。さらに `start_round` は保留決定の持ち越しを `debug_assert` で
    禁じており（`src/model.rs:1184`）、帰宅フェイズで停止するなら契約変更が要る。
- 解放に必要な最小設計（**未実装・設計のみ**）:
  1. 収穫内の停止・再開契約（`Continuation` と `ChainStep` の拡張、`harvest()` の途中コミット）。
  2. 帰宅フェイズの dispatch 地点＋プレイヤー別の使用スペース記録。
  3. 得点準備フェイズ（置いた食料を記録してから `score` を呼ぶ）。
  4. プレイ時ラウンドの記録。`state_hash` の v5 固定契約（`model.rs`）に触れるため、
     台帳と同じ「`integrity_hash` のみに含める」方式か、v6 へ上げるかの設計判断が必要。
- 文献で解消したルール解釈（**人間の決定待ち 0 件**。別セッションでの確認は不要）:
  - A100 の頻度 = **1ラウンド1回**。英語一覧（`cardlist_en`）が「累積スペースから3人以上を
    戻したなら、食料1で1点を買える」という単一の条件文で、spec の `every_round` と一致する。
    日本語ページ（`?p=3325`）の「戻すたびに」はラウンドごとの条件成立を指す表現と読む。
  - C099 の置き方 = **空き畑1つにつき 1/4/7 を置くと 1/2/3 点**。英語一覧が「1/4/7 の食料を
    置いた畑1つにつき 1/2/3 点」と明示する。2/3/5/6 を置いても点にならない。
  - 同じ英語一覧で4枚の効果文（C098 の「ちょうど木材1＋食料1」、D099 の「1人につきレンガ1、
