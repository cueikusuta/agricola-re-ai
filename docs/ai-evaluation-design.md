## 1. 目的・範囲・前提

### 1.1 目的

対戦AIの版（バージョン）どうしを、あとから比較可能な形で評価するための基盤を設計する。対象は次の4点。

1. 自己対戦の回し方（対戦数・seed管理・席順偏りの除去・版間対戦の組み方）。
2. 評価指標の定義と集計（首位率・期待順位・得点差、信頼区間、版の優劣判定）。
3. 10-7ドラフトの評価（ドラフト単体の切り出し計測と、対戦結果への接続）。
4. 計測の記録形式（版どうしの比較が将来も成立するスキーマと保全）。

決められない点は決めずに §6「未決定の一覧」へ理由付きで残す。

### 1.2 前提（本タスクで指定された決定事項）

| # | 前提 | 本書での扱い |
|---|---|---|
| P1 | 目的関数は二層。物差しは辞書式「首位率 → 期待順位」 | §3 の判定規則。ロードマップ§3の意思決定順位「首位率 → 期待順位 → 得点差 → 計算コスト」の上位2層を判定物差しとして固定する。得点差・計算コストは補助記録であり、首位率の判定を覆す根拠にしない |
| P2 | 探索と学習は得点差（自分の得点 − 相手全員の平均得点）を使う | §1.3 で報酬として固定。ロードマップ§3.4の報酬候補 R-B に相当する |
| P3 | 自分の損になる妨害はしない | §1.4 の方策制約。ルールエンジンの合法性判定は変更しない（ルールエンジンは AI が提案しない合法手も受理する） |
| P4 | 最終形は4人戦のみ、10-7ドラフト | 最終評価モードを `players=4` × `draft_10_7_simultaneous` に固定（§1.5）。2人戦・カードなし等は足場・回帰用であり、最終形の成績と合算しない |
| P5 | PUCT は `prior_temperature=6` が標準採用 | 凍結構成 `puct-s32-d2-c1.5-pt6-vt8-terminal-rl0-fp0` を現行基準とする（§1.6） |

### 1.3 二層の目的関数と報酬の分離

- **評価の物差し（辞書式）**: まず首位率で版を比べる。首位率の差が統計的に判別できない場合に限り、期待順位（小さいほど良い）を第二層として参照する。得点差・計算コストはロードマップ§3に従い補助指標として必ず記録するが、採用判定の根拠にはしない。「有意差がない」ことを「同等」の証明と混同しない（ロードマップ§3.2）。
- **探索・学習の報酬**: `score_margin = 自分の最終得点 − 相手全員の最終得点の平均`（4人戦では相手3人の平均）。最終得点は公式準拠のタイブレーク・終了時カードボーナスを含む `standings_with_cards` 系の得点を使う。これはロードマップ§3.4の R-B であり、本タスクの前提P2により標準報酬として固定する。
- **分離の原則**: 報酬は連続値で教師信号を得やすい一方、4人戦では「得点差は大きいが2位」の手を過大評価し得る（ロードマップ§3.4）。**学習目標＝最終目的ではない。** 報酬・探索・学習のあらゆる変更は、最終的に首位率（物差し第一層）で検証する。首位率を改善できない代理報酬の改善は採用根拠にしない。
- 正本との整合注記: ロードマップ§3.4は報酬を「実験対象」とし R-A（首位クレジット）/ R-B（得点差）/ R-C（複合）の比較を求めている。本書は前提P2を新しい決定として R-B を標準に固定するが、R-A/R-C を対照として残すかどうかは §6 に未決定として残す。ロードマップの「首位率で最終検証する」原則は変更しない。

### 1.4 「自分の損になる妨害はしない」の設計上の扱い

これは**方策（候補生成・報酬）側の制約**であり、ルール変更ではない。

- 4人戦の得点差報酬は、自分だけが損をする妨害の多くを自然に罰する。自分が `c` 点失い相手1人が `h` 点失う場合、得点差の変化は `−c + h/3` であり、`h > 3c` のときのみ正になる。しかし**この条件を満たす自損妨害は得点差報酬では正当化されてしまう**ため、報酬だけでは前提P3を保証できない。
- したがって、候補生成フィルタ・報酬ペナルティ・辞書式報酬（自分の得点を先に置く）などの強制機構を別途設計する必要がある。どの機構を採るかは実験なしには決められないため §6 に残す。
- 現行の検証済みプールは「他人に影響する効果」を M10-ADVANCED として隔離しており（`docs/four-player-card-rollout-m10.md` §4.1）、短期の評価対象では自損妨害カードはほぼ構造的に不在。この制約が本格化するのはプール拡張時であり、それまでに機構を決定する。
- 評価側では、自損妨害の発生を監視する代理指標（例: 妨害系カードをプレイした試合での自己得点損失の分布）を記録項目として §5 に含める。操作的な検出定義は §6 の未決定。

### 1.5 最終評価モード

- `players=4`、カードあり（公式照合済み・4人適格・実装済みプール）、ドラフト方式 `draft_10_7_simultaneous`（職業10枚＋小進歩10枚から各7枚を7回の同時ピックで選択、各束3枚破棄）。
- 「10-7ドラフト」はパス式ドラフトを指す。`choose_10_7`（非ドラフト選択）はロードマップ§4.4・`docs/draft-protocol-m11.md` §2 で**別モード**として定義されており、本書の評価対象に含めない。
- 確定済みのプロジェクト仕様（#155、2026-11-09）: 受け渡しは両種別とも**右回り固定**、ドラフト開始前に初回スタートプレイヤーを**ドラフトseedと独立した乱数ストリーム**で抽選して公開し、ゲーム開始へ引き継ぐ。
- 前提条件: M10 G1（4人適格・公式照合済み・実装済みの職業40枚＋小進歩40枚）、M11の観測履歴・再演受け入れ、#155の残る慣行（同時ピックの順序・時間切れ方針等）。これらが未達のうちは、最終モードの正式評価は実施せず、フィクスチャによる機能検証のみを行う（§4）。
- 2人戦・カードなし・7-7 等の既存モードは、回帰・足場・アブレーション用として残す。**モード間の結果を無条件に合算しない**（ロードマップ§3.1）。

### 1.6 標準PUCT構成（凍結基準）

- 現行標準: `puct-s32-d2-c1.5-pt6-vt8-terminal-rl0-fp0`（simulations 32 / depth 2 / c=1.5 / **prior_temperature=6** / value_temperature=8 / leaf=terminal / root_limit=0 / final_prior=0）。
- 採択根拠: Issue #219 の事前登録比較。[Actions Run 42654611147](https://github.com/cueikusuta/agricola-re-ai/actions/runs/42654611147)（4人カードなし・固定32sim・未知seed 985000–985249・1,000試合/arm）で旧pt3構成比 **+8.05pp・95%CI [+5.2, +11.0]pp**、事前登録基準（点推定≥+5pp かつ CI下限>0）を満たして採用。詳細は `docs/m13-puct-ablation-219-2026-11-09.md` §6。#263 で `PuctConfig::default()` に反映済み（回帰テスト `shipped_default_is_the_adopted_pt6_configuration`）。
- 本書ではこの構成を「**凍結基準PUCT**」と呼び、版間比較の固定相手・鏡像対照に使う。構成の一部でも変えた候補は**別の config ID / policy version** として登録し、同名上書きを禁止する（`scripts/paired_eval_stats.py` は config ID と行内スカラーの一致を既に検証する）。
- 限界の再掲: pt6採択はカードなし4人・固定シミュレーション数での証拠であり、同一思考時間・カードあり・ドラフトでの強さは未証明。最終モードでは §2 の条件で再評価する。

## 2. 自己対戦の回し方

### 2.1 二つの用途を分離する

| 用途 | 目的 | seedプール | 思考予算 | 相手構成 | 記録 |
|---|---|---|---|---|---|
| **評価試合** | 版の強さの判定 | locked test（未知seed） | マニフェスト固定（§2.7） | 凍結基準で固定（§2.5） | 1試合1行JSONL＋集計レポート（§5） |
| **学習用自己対戦** | 教師データ・方策改善 | train のみ | オフライン予算（10秒制約の対象外） | 過去版混合可（§2.6） | `EpisodeRecord`（再演検証付き） |

両用途の試合・seed・結果を混同しない。学習データの生成量・相手混合は G0〜G3 ゲートに従う（ロードマップ§4.5、AGENTS.md 12）。

### 2.2 試合単位とarm構成（評価試合）

既存 `paired_eval` の契約を最終モードへ拡張する。

- **1ブロック = 1 seed**。4人戦の1ブロックは `4席 × 2 arm = 8試合`。1,000試合/arm は **250ブロック**で構成する（2人戦なら500ブロック×2席。最終形は4人戦のみ）。
- **candidate arm**: 焦点席に候補版を置き、残り3席は凍結基準版で固定する。焦点席はブロック内で全4席を1回ずつ巡回する（座席ローテーション）。
- **baseline arm**: 全4席を凍結基準版にする**鏡像対照（mirror control）**。candidate arm と同一 seed・同一席条件で実行する。
- 一意キーは `(condition_id, block_index, arm_id, candidate_seat)`。再試行も同じキー・同じseedで行い、二重計上を禁止する。集約時にキーの重複・欠落・条件違いを拒否する（fail closed）。
- `condition_id = SHA256(players, ruleset, deck_content_hash, draft_mode, opponent_profile, compute_budget, engine_version)`（`docs/github-actions-mass-simulation-m8-3.md` §3 の定義に `draft_mode` を追加）。
- 集計レポートの `comparison_design.head_to_head=true` かつ `mirror_baseline=true` を直接対戦の条件とする。共通相手ベンチマーク（両armが同じ固定場に別々に対戦）は `head_to_head=false` であり、直接対戦の結果として報告しない。
- **最終モードの版は「ドラフト方策 × ゲーム方策」の組**で識別する。arm = `(draft_policy_id, game_policy_id)`。ドラフトだけ・ゲームだけの寄与分離は §4 で扱う。

### 2.3 対戦数とseed管理

**対戦数**

- 初期評価バッチは **1,000試合/arm**（比較全体で2,000試合）。これは計測開始点であり、+5ppを確定させる固定試合数ではない（ロードマップ§3.2）。
- 本実行の前に **10〜20ブロックのパイロット**を回し、完走率（`finished=false` が0）・飽和（§3.4）・1シャード所要時間と本実行への外挿・Artifact整合を確認する。**パイロットの数値は強さの主張に使わない。**
- 初期1,000試合で区間が0を跨いだ場合、観測したブロック差の標準偏差 `s_d` から必要ブロック数を `ceil(((1.96+0.84)*s_d/0.05)^2)`（検出力80%・両側5%・差5pp）で再推定する。**追加上限（例: 1,000ブロック）と途中解析の予定（初期→事前宣言の1回追加→最終判定）を実行前にマニフェストへ固定**し、無制限な検定の繰り返しを禁止する。逐次検定に切り替える場合はα消費を別途設計する。

**seedの算術とシャード**

- `block_seed = seed_start + block_index`（算術オーバーフローは失敗）。`shard_id = block_index % shards`。**同一ブロックの arm×seat をシャード境界で分割しない。**
- 1実験は1オフセット（`seed − block_index` が全行で同一）。集約側はこれを検証する（`evaluation_seed_blocks`）。

**seedレジストリ（使用済み・予約済み範囲）**

新規評価のseed範囲は、実行前のマニフェスト登録時に下表と既往Runのマニフェスト照合で重複を拒否する。計画のみで未実行の範囲も予約扱いにする。

| 範囲 | 用途 | 出典 |
|---|---|---|
| 64000–64003 | #212 小規模pilot（4ブロック） | `docs/ai-experiments-m12-m14.md` §11 |
| 920000台 | G0 証拠用評価 | `docs/ai-experiments-m12-m14.md` §11（G0 seed 920000台） |
| 940000–940499 | 条件C計画（2人・直接対戦、未実行） | `docs/m13-head-to-head-plan.md` §3 |
| 950000–950249 | 条件D計画（4人・50ms、未実行） | `docs/m13-head-to-head-plan.md` §3 |
| 965000–965249 | #212 正式PUCT対MCTS（実行済み） | `docs/ai-experiments-m12-m14.md` §13 |
| 971000–971009 | #219 アブレーションpilot | `docs/m13-puct-ablation-219-2026-11-09.md` §3 |

ローカル小規模検証のseed（例: 911・700台・100:1600 の分割例）は正式レジストリ外だが、正式範囲と衝突させない。最終モード用の新規範囲の割当は §6 の未決定（プール版・初期状態との整合確認が必要なため）。

**分割とロック（train / validation / test）**

- `src/dataset_split.rs` の分割Manifestを使う。範囲非重複・seed帰属・seed一意性・再演一致・provenance一様性・**同一 `initial_state_hash` の分割跨ぎ禁止**・非公開情報非混入を fail closed で検査する。
- seed値だけでなく**生成器バージョンとデッキ版**でも分割を区別する。seedが違っても同一初期局面なら test は「未知の局面」ではない。
- **test は最終判定専用**にロックする。学習・調整・教師ラベル作成・ハイパーパラメータ選択に使わない。test を見ながら調整した場合、その test は探索用に降格し、新しい未知seedで最終判定をやり直す。
- 同一ブロックの席を分割をまたいで分けない。

### 2.4 先手・席順の偏りの消し方

1. **座席ローテーション**: 焦点席は各ブロックで全4席を巡回する。席別の首位クレジット（`*_first_credit_by_seat`）と席間spreadを集計レポートに記録し、特定席への偏りを監視する。
2. **初回スタートプレイヤー**: ドラフト開始前にドラフトseedと独立した乱数ストリームで抽選・公開し、ゲームへ引き継ぐ（#155確定仕様）。試合ごとに `start_player` を記録し、スタートプレイヤー席別の成績を診断値として集計する。
3. **鏡像対称性の検査**: 4人戦の鏡像armの首位クレジットは対称性から **約25%** に近づくはずである。大きく偏る場合は座席・開始プレイヤー・ドラフト受け渡しの非対称を疑い、**差の解釈を止める**（`docs/m13-head-to-head-plan.md` §3）。
4. **ドラフト受け渡しの非対称**: 右回り固定のためパケットの流れは席に対して非対称になる。座席ローテーションで平均化し、単一席のみの評価を禁止する。
5. **配布の公平性**: 同一seedなら両armで同一の配布。同一カードは全プレイヤーで一度しか配らない。人数適格・公式照合済みフィルタ後のプールから配布する。
6. **ハードウェア偏り**: time-budgeted の結果は壁時計依存であり、同一SHA・同一seedでもビット単位一致は保証しない（再現性の主張は simulation-capped に限る）。`cpu_model` を記録し、異なるCPU間の時間比較は比のみ・注記付きとする（`docs/perf/` の運用慣行）。

### 2.5 版の違うAI同士の対戦の組み方

**版の同一性**

- 版は `policy_id + version + config_id + weights_hash（学習モデルがある場合）+ details_policy_id + code_sha` で識別する。**同名PUCTでも設定が違えば別ID**として登録し、データ混在を集約側で拒否する（`paired_eval_stats.py` の config ID 検証）。
- 凍結基準は「構成ID＋コードSHA＋（将来の）重みハッシュ＋ドラフト方策ID」で固定する。`paired_eval` の `--baseline-puct-*` は8フラグをすべて明示するか、まったく指定しないかの二択しか許さない fail closed 設計であり、部分凍結（残りが候補値へ沈黙追従する事故）を実行前に拒否する。

**比較の組み方（優先順）**

| 種類 | 構成 | 位置付け |
|---|---|---|
| **一次比較（主要）** | 候補1席 vs 凍結基準3席＋基準鏡像arm。同一seed×全4席。locked test・事前登録1件 | 採用判定の唯一の根拠（§3） |
| 鏡像対照 | 凍結基準の同士（全4席） | 対称性検査。単独では強さの証拠にしない |
| 過去版リーグ（探索的） | 過去版どうしの総当たり・ペア記録 | 非推移性の監視・頑健性探索。一次比較と合算しない |
| 混合場（探索的） | 相手3席に過去版を混ぜる | 特定相手への過適合の検出。探索的と明示 |
| 共通相手ベンチマーク | 両armが同じ固定場に別々に対戦 | `head_to_head=false`。直接対戦と混同しない |

**非推移性と基準の昇格**

- 版の強さは非推移的になり得る（A>B、B>C でも A>C とは限らない）。**採用判定は事前登録した直接比較のみ**で行い、リーグ結果から推移的に採用を導かない。大域評価（Elo等）の導入は §6 の未決定。
- 基準昇格（提案）: 候補が採用されたら、**次の実験登録時に**その版を新しい凍結基準にする。旧基準は構成ID付きで archive に残し、各Runの「どの版を基準にしたか」をマニフェストに記録する。過去データを遡って書き換えない。昇格のタイミング・手続きの詳細は §6 に残す。
- 相手席は常にその方策自身の既定設定で動く（time-budgeted モードでは焦点席の停止規則が壁時計であり、相手席の探索回数は相手方策の既定。#219 レビュー記録）。この非対称はマニフェストに明記する。

### 2.6 学習用自己対戦（データ生成）

- train seed のみで生成し、`record_self_play` → Episode API → `EpisodeRecord`（schema_version=1）として記録する。全件を再演検証し、学習サンプルは `assert_public()` で非公開情報の非混入を検査する。ドラフト履歴は各席が正当に観測した `DraftEpisode.views[seat]` からのみ渡す。
- 相手構成は過去版の混合を許す（単一相手への過適合回避）。混合比は事前宣言し、**評価場の固定とは独立**に管理する。
- オフライン生成には1手10秒制約を適用しない。ただし最終受け入れ対象の方策は §3.5 の10秒観測を別途満たす必要がある。生成CPU予算・所要は評価とは別記録にする。
- データセットはモード別・生成器版別・デッキ版別に分離する（provenance一様性チェックが混在を拒否）。

### 2.7 実行基盤と予算モード

- **実行場所**: 大量試合・AI比較は原則 GitHub Actions の GitHub-hosted 標準CPU（`ubuntu-24.04`）。ローカルは小規模スモーク・故障再現・デバッグのみ（AGENTS.md 8/13）。有料GPU・大型ランナーは明示判断なしに使わない。
- **起動**: 強さの実験は `workflow_dispatch` 等で明示起動する。通常PRの必須CI（60秒目標）に大量試合を組み込まない。main統合時の `Mode-wide Simulator Verification` / `G0 gate` 自動起動は安定性・証拠のゲートであり、強さの主張ではない。
- **予算モードは2種類を混ぜない**:
  - `simulation-capped`: 探索回数固定。決定論的再現（ビット単位一致）が可能。回帰・等回数アブレーション用。
  - `time-budgeted`: 探索＋詳細決定を1つの時計で束縛（`DecisionBudget`・`detail_reserve_ms`）。**同一時間予算の比較を主要結果**とする（ロードマップ§3.3・M13）。予算値はマニフェスト固定。最終モードの標準予算値は §6 の未決定。
- シャードはブロック単位で分割し（250ブロックなら8シャード等）、シャード上限時間内に収まるようパイロットで外挿する。集約は欠落・重複・失敗・再演不一致があれば赤判定とし、不完全結果を強さの証拠にしない。
- 全試合で再演ハッシュを検証する（`replay_verified=true`・14ラウンド完走を必須）。完走は安定性の試験であり、ルール正確性の証明ではない（ロードマップ§4.1）。

## 3. 評価指標の定義と集計・版の優劣判定

### 3.1 指標の定義

すべて**コーディネータ側の権威状態**（エンジン内部の完全状態）から計算する。AIの観測から計算しない（観測は非公開情報を含まないため、順位・得点の正本たり得ない）。

| 指標 | 定義 | 備考 |
|---|---|---|
| 最終得点 | `standings_with_cards` 系の得点（印刷得点＋終了時カードボーナス）。公式準拠の資源タイブレーク後に competition rank を付与 | rank = 1＋（より高得点、または同得点で資源が多いプレイヤー数）。同得点・同資源は同順位とし、次の順位は同順位者数だけ飛ばす |
| **首位率（首位クレジット）** | 各試合で `credit = 1/k`（焦点席が1位のとき。`k` = 同率1位者数）、それ以外0。armの全試合平均 | ロードマップ§3.1。**評価用の勝利クレジットであり、公式ルールの順位判定を変更しない** |
| 期待順位 | competition rank（1〜4）の平均。小さいほど良い | 行には焦点席の rank を `expected_rank_observation` として記録 |
| **得点差** | `score_margin = 焦点席の最終得点 − 相手3人の最終得点の平均` | 探索・学習の報酬（P2）と同一定義。平均と分布を記録 |
| 計算コスト | 焦点席の1手時間 p50/p95/p99/max、タイムアウト率、フォールバック率、games/sec、decisions/sec、CPU（wall）秒 | §3.5 の10秒観測に使う |

参考値として **単独1位率**（`solo_first_rate`）・**同率首位を含む首位到達率**（`first_reach_rate`）・**同率1位が発生した試合の割合**（`tied_first_game_rate`）を首位率と分けて記録する（ロードマップ§3.1）。これらは `paired_eval_stats.py` に実装済み。

### 3.2 集計方法（seedブロック・ブートストラップ）

- **独立標本単位は seed ブロック**。ブロック `b` の差を `d_b = mean_seats(credit_candidate − credit_baseline)` とする。**4席を4つの独立試合として数え上げない**（同一seed・同一配布由来の相関があるため）。
- 点推定 = `mean(d_b)`。差の95%区間は**ブロック・ブートストラップ（percentile法）**で推定する: ブロックを復元抽出で再標本化し、**反復10,000回・bootstrap seed 20261106**（既存実装の固定値。手法・反復数・seedは評価コードに固定してレポートに記録する）。
- 補助として各armの首位率の95%区間を併記してよいが、単純二項近似は**複数座席・同点・共有seedの相関を扱っていない**ことを明記する（ロードマップ§3.2）。
- **期待順位差・得点差差**も同一のブロック構造（`d_b^rank`, `d_b^margin`）で集計し、同じブートストラップ規約で区間を出す。
- 必要ブロック数の再推定: `ceil(((1.96+0.84)*s_d/0.05)^2)`（`s_d` = `d_b` の観測標準偏差）。実装済み（`required_seed_blocks_estimate_5pp_80pct_power`）。
- 参考: 独立二群近似では5pp差・80%検出力で各群約1,600試合が目安だが、4人戦・同率・座席相関・ペア設計で必要数は変わるため**固定基準にしない**（ロードマップ§3.2）。

### 3.3 版の優劣判定（事前登録・辞書式二層）

判定は**実行前にマニフェストへ登録した規則**で行い、結果を見てから規則を変えない。一次比較（候補 vs 凍結基準・locked test・§2.5）に対する判定区分:

**第一層: 首位率**

| 区分 | 条件 | 扱い |
|---|---|---|
| **採用（目標達成）** | 点推定 ≥ +5pp かつ 差の95%CI下限 > 0 | 暫定採用。基準昇格は §2.5 の手続き |
| **改善確認（目標未達）** | CI下限 > 0 だが点推定 < +5pp | 改善として記録。**+5pp目標の達成にはしない**（ロードマップ§3.2） |
| **判定保留** | CIが0を跨ぐ | 必要ブロック数を再推定し、事前宣言した上限・回数で追加計測。最終判定時点で再判定 |
| **不採用** | 点推定 ≤ 0（特にCI上限 < 0 なら明確な劣化） | 採用しない。理由と条件を記録 |

**第二層: 期待順位（第一層が統計的に判別できない場合のみ）**

- 首位率の差が判別できない（判定保留・未判定）ときに限り、期待順位差のブロック区間を参照する。期待順位が有意に小さい版を「期待順位で優位（首位率は未判定）」として**報告上の順位付け**に使う。
- **第二層は採用判定の代替ではない。** 採用（目標達成）は常に第一層の基準を満たすことを要求する。ロードマップの「得点差だけで強いAIと断定しない」「首位率の悪化を下位指標で隠さない」原則を維持する。
- 両層とも判別できない場合は「**未判定（同等の証明ではない）**」とする。得点差・計算コストはロードマップ§3の順位に従い補助情報として記録するが、採用根拠にしない。
- 第二層の統計規約（CIが0を除外することを要求するか、同等性マージンを置くか）は未決定（§6）。確定するまで第二層の出力は記述的参照に留める。

**複数比較の規律**

- validation で一次候補を1つ選び、locked test では**事前登録した一次比較1件**のみを主要検定とする。多数の候補・条件を試した最大値を無補正で採用しない（`docs/ai-experiments-m12-m14.md` §2）。
- 探索的比較（リーグ・混合場・アブレーション）は「探索的」と明示し、主要判定と合算しない。

### 3.4 条件の妥当性ガード（判定の前に検査）

| ガード | 条件 | 不合格時の扱い |
|---|---|---|
| 飽和（天井） | いずれかのarmの首位率 ≥ 95%（`saturation.ceiling_limited`） | その条件は+5ppを判別できない。**差を強さとして報告せず**、相手場・モードを変える |
| 鏡像対称性 | 4人戦鏡像armの首位率 ≈ 25% | 偏りが大きければ座席・先手・ドラフト非対称を疑い、差の解釈を止める |
| 直接対戦性 | `comparison_design.head_to_head=true` | false の結果を直接対戦として書かない |
| 条件一様性 | search_mode・予算・デッキハッシュ・provenance・config ID が全行一致 | 不一致は集約拒否（fail closed） |
| 完全性 | 全行 finished・14ラウンド・`replay_verified=true`・キー集合完全 | 欠落・重複・失敗があれば赤判定。不完全結果を証拠にしない |
| 10秒主張の資格 | time-budgeted・予算 ≤ 10,000ms・`whole_decision_budget_enforced=true` | simulation-capped の結果から10秒遵守を主張しない |

### 3.5 1手10秒上限の受け入れ計測

- 測定対象は**対戦中のCPUの1回の意思決定**（ワーカー配置・カード・資源・配置などの詳細決定を含む）。**ドラフトの1ピック（職業＋小進歩の同時選択）も独立した1意思決定**として同じ上限で評価する（ロードマップ§3.3）。
- 予算は探索＋詳細決定を1つの時計で束縛し、詳細用の予約（`detail_reserve_ms`）を予算内に確保する。協調的 deadline の観測許容は既存規約どおり `max(予算の1%, 1ms)` とし、厳密な超過（overshoot）も記録する。
- 検索開始前から必ず合法な初期候補を確保し、期限切れ時はその候補へフォールバックする。未確定の不正手・パニックを返さない。
- **最終受け入れは観測した全焦点手が10秒以内**（`focus_observed_all_decisions_within_10s`）を要求する。平均・中央値・p95・p99・最大・タイムアウト率・フォールバック率を記録する。
- 基準CPU・実行モード（Rust release）・`cpu_model`・rustc版・測定時刻を記録する。ハードウェア差で結果が変わるため、異なるCPU間の絶対時間比較はしない（§2.4）。
- オフライン学習・大量バッチには10秒制約を適用しない。バッチ速度を10秒遵守の証拠にしない。

### 3.6 報告の様式

一次比較の報告には次を必ず含める: 両armの首位率・期待順位・得点差（平均と分布）、差の点推定と95%CI、席別内訳とspread、参考値3種（単独1位率・首位到達率・同率試合率）、ガードの結果（飽和・鏡像・head_to_head）、判定区分（§3.3）、必要ブロック数再推定、試合/秒・意思決定/秒・1手時間分位・タイムアウト/フォールバック率、実行SHA・Run URL・Artifact・seed範囲・bootstrap規約。

様式の先行例: `docs/m13-puct-ablation-219-2026-11-09.md` §6 の採択判定表（pt6・+8.05pp・CI [+5.2, +11.0]pp）。**数値の改善だけでルールの正しさを判定しない**（ロードマップ§6.6）。

## 4. 10-7ドラフトの評価

### 4.1 対象モードと前提条件

- 対象は `draft_10_7_simultaneous`（4人・職業10＋小進歩10から各7枚を7回の同時ピックで選択・各束3枚破棄・受け渡し右回り固定・ドラフト前に初回スタートプレイヤー抽選）。`choose_10_7`（非ドラフト選択）は別モードであり対象外（§1.5）。
- **前提条件（未達のうちは正式評価をしない）**:
  1. M10 G1: 4人適格・公式照合済み・実装済みの職業40枚＋小進歩40枚（`card_pool_report` の実測で確認。古い文書の枚数記載を流用しない）。
  2. M11: ドラフト観測履歴（`own_observation_history`・公開ピック・残り枚数）の受け入れ、保存・再演整合。
  3. #155 の残る慣行（同時ピックの順序・時間切れ方針・人数別例外）の確定。
- 前提未達のうちは `test_fixture`（FIX-*）プールで**機能検証のみ**を行い、「実戦の強さ」と表示しない。先行例: `compare_draft_ais` は機能比較であり強さ計測ではないと明記されている（`src/draft_ai.rs`）。

### 4.2 二段階の計測

ドラフトの評価は次の2段に分ける。**L1（ドラフト単体）だけでは強さを主張しない。**

| 段 | 測るもの | 相手・条件 | 判定への使い方 |
|---|---|---|---|
| **L1: ドラフト切り出し** | ドラフト方策単体の品質・合法性・速度・情報利用 | ドラフトのみ実行。ゲームは始めない | 開発・選別用の代理指標。採用判定の根拠にしない |
| **L2: ドラフト→対戦接続** | ドラフトの差が14ラウンドの対戦結果に与える効果 | ドラフト後に固定ゲーム方策で完走 | §3 の物差し（首位率→期待順位）で判定 |

### 4.3 L1: ドラフトだけを切り出して測る

**実行設計**（`run_draft` / `compare_draft_ais` の拡張）:

- 同一seedで配布を固定し、**焦点席に候補ドラフト方策、残り3席に凍結参照ドラフト方策**を置く。ブロック内で全4席を巡回する（§2.4）。鏡像対照（全席参照方策）も同seedで実行する。
- 1ピック = 職業1＋小進歩1の同時選択を**1意思決定**として扱う。1ピック10秒の上限・フォールバックを §3.5 と同じ規約で計測する。
- 参照方策は現時点では `CardValue` / `Synergy`（公開カタログの宣言点数・費用・効果タグのみを使う手作り評価）。**参照が弱すぎる条件は天井に張り付き判別力を失う**ため、参照の更新は版管理し、飽和ガード（§3.4）をL1にも適用する。探索ベースの強い参照ドラフト方策は未実装（§6）。

**L1の指標**:

1. **合法性・完全性・再現性**: 全ピックが `offered_ids` 由来で合法、枚数不変条件（選択7＋残束3＝配布10、カードID重複0）、ドラフトイベント列の再演ハッシュ一致、固定seedでのビット単位再現。
2. **速度**: 1ピック時間 p50/p95/p99/max、タイムアウト率、合法フォールバック率。
3. **手札品質の代理指標**（公開カタログと正当な観測履歴のみから計算）: 印刷得点合計・費用加重価値・効果系統カバレッジ・シナジー。既存 `base_value`（`points*30 + tags*8 − cost`）は粗い暫定式であり、**L2との相関検証なしに選別根拠にしない**（§4.5）。
4. **情報利用の監査**: 観測履歴（見た束・渡した束・公開ピック・残り枚数）を使う方策と、使わない消融armを同条件で比較し、**ドラフト記憶の寄与**を測る。非干渉テスト（他人の非公開手札・内部seedだけが異なる2状態で観測と挙動が同一）を必須とする。
5. **自損妨害の監視**: 妨害系カードの選択頻度と、それを選んだ場合の自己手札品質損失を記録する（§1.4。操作的検出は §6）。

**L1の集計**: seedブロック単位で §3.2 と同じブートストラップ規約を使う（1ブロック = 1 seed × 全席 × 両arm）。ただしL1の差は「ドラフト代理指標の差」であり、対戦強さの差ではないとレポートに明記する。

### 4.4 L2: 対戦結果とつなぐ

**寄与分離の実験設計**:

- **ドラフト寄与arm**: 焦点席のドラフト方策だけを候補版にし、**ゲーム方策は全4席で凍結基準PUCT（pt6）に固定**する。対照armはドラフトもゲームも凍結基準。同一seed×全4席ローテーションで14ラウンド完走させ、§3 の指標・集計・判定をそのまま適用する。
- **最終形arm（フルスタック）**: ドラフト方策・ゲーム方策の両方を候補版にする。最終形の採用判定はこちらで行う。
- **要因分解（探索的）**: (ドラフト新旧) × (ゲーム新旧) の2×2を同一seed群で実行し、ドラフト・ゲーム・交互作用の寄与を分解する。一次比較は事前登録1件とし、2×2全体を主要検定にしない（§3.3）。
- 同一seedは同一配布を保証するが、ピックが違えば初期手札が変わり対戦軌跡は分岐する。**対応付けはseedブロック単位**であり、軌跡単位のペアではない。ブロック・ブートストラップはこの設計でそのまま機能する。
- **交互作用の注意**: ドラフトの良し悪しはゲーム方策に依存する（現行PUCTに良い手札が将来の方策に良いとは限らない）。**ゲーム方策を更新したらL2を再実行**し、古いL2結果を新しい方策の証拠に流用しない。
- ドラフト由来の `start_player` はゲームへ引き継がれ、全試合に記録する（§2.4）。ドラフトイベント・各席の最終手札・破棄カードはコーディネータ側記録に含め、AI観測には出さない（§5）。

### 4.5 L1とL2の接続（代理指標の検証）

- L1の手札品質代理指標とL2の対戦成績（首位クレジット・得点差）の**ブロック単位相関**を分析として報告する。相関が確認できない代理指標は選別に使わない。
- L1で良くてもL2で改善しない場合（例: 高得点カード偏重で序盤の食料・労働力が不足）、その失敗を記録し代理指標を修正する。**L1の改善をL2の改善と混同しない。**
- 接続の定量基準（どの相関・どのL2差をもって代理指標を「検証済み」とするか）は未決定（§6）。初回のL2実測データができるまで固定しない。

### 4.6 ドラフト評価の記録

L1/L2 とも §5 の記録形式に従い、加えて次を残す: ドラフトイベント列（各席の正当な観測投影を含む）・ドラフト再演ハッシュ・`start_player`・ピック別時間・参照ドラフト方策の版ID・プール版（`card_set_hash` と40+40ゲート実測）・破棄カードID（コーディネータ側のみ）。

## 5. 計測の記録形式

**目的: あとから版どうしを比べられること。** そのためには「どの条件で・どの版で・どのseedで・どの規約で集計したか」が機械可読に固定され、条件の違いが暗黙に混ざらないことが必要である。本章のスキーマは**設計提案（未実装）**であり、既存実装のフィールドは §1.7 の基盤を正本とする。

### 5.1 記録の層

| 層 | ファイル | 役割 | 既存基盤 |
|---|---|---|---|

### 5.4 集計レポート（既存 ＋ 拡張）

既存 `paired_eval_stats.py` のレポート（首位クレジット・差・95%CI・席別内訳・参考値3種・`comparison_design`・`saturation`・必要ブロック数・速度・config ID・10秒観測フラグ）に、次を追加する:

- **判定区分**（§3.3）: `decision.layer1_category`（adopted / improvement_below_target / hold / rejected）、`decision.layer2_rank_reference`（期待順位差と区間・参照可否）、`decision.final`（未判定を含む）。
- 期待順位差・得点差差のブロック区間（§3.2）。得点差は平均に加えて分布（分位・ヒストグラム）を記録する。
- ドラフト節（L1/L2）: ピック時間分位・フォールバック率・手札代理指標・L1↔L2相関（§4.5）。
- ガード結果一覧（§3.4）と、ガード不合格時の「判定不能」明示。

### 5.5 版どうしの比較可能性の規則

1. **直接比較は `condition_id` 一致が前提**。モード・デッキ版・ドラフト方式・予算モード・予算値・相手構成のいずれかが違えば別条件であり、合算しない。
2. provenance（engine/rules/cards/code/AI版）の一様性を集約側で強制し、不一致は fail closed で拒否する。config ID と行内スカラーの矛盾も拒否する（既存実装）。
3. **未知の `schema_version` は拒否**する。旧形式行（config IDなし等）は履歴として受理するが、新形式と暗黙に混在させない。
4. 異なるRun間の比較は、同一 `condition_id`・同一bootstrap規約の場合のみ「比較可能」と表示する。条件をまたぐ主張は**橋渡し実験**（同一seed群で両条件を実行）を別途登録して行う。
5. **過去データを書き換えない**。基準が昇格しても旧Runは旧基準の記録として残し、各Runのマニフェストが「どの版を基準にしたか」を保持する（§2.5）。
6. 数値は実ファイルから再計算する。試合数・hashを手入力した証拠は受理しない（`g0_evidence.py` の規約。G0 evidence v2）。

### 5.6 保全（長期archive）

- GitHub Actions Artifactは保持期間で消える。**正式Runはリポジトリ内 `docs/eval-runs/<date>-<slug>/` に保全する**（`run-manifest.json`・`report.json`・`shard-N.matches.jsonl.gz`・evidence）。先行例: `docs/m13-runs/`・`docs/g0-runs/`。ポインタ方針は `docs/perf/` のREADME慣行に倣う。
- 保全対象は「あとから版を比較するのに必要な最小完全セット」（マニフェスト・全試合行・レポート・証拠）。生ログはArtifact側に残し、長期保全は圧縮試合行とする。
- 秘密情報（内部seedのAI入力・非公開手札の観測流出）は記録に含めない。コーディネータ側フィールドとAI観測の境界（§5.3）を保全時も保つ。

### 5.7 スキーマ進化

- `schema_version` は単調増加。読取側は未知版を拒否（fail closed）。
- 追加フィールドは旧行で欠落を許す（後方互換）。**意味の変更は新版＋移行フィクスチャ**（旧版で生成した実データを新版が読めることの証明）を伴う。旧データを無言で再解釈しない（ドラフトschema v1→v2の先例）。

### 5.8 学習データとG0証拠（別系統）

- 学習データは `EpisodeRecord`（schema_version=1）のJSONL。全件再演検証・`inspect_dataset` による件数/重複seed/破損/provenance検査・`training_samples(viewer)` の `assert_public()` を経て分割Manifestへ渡す。
- G0証拠は evidence v2（`matches_sha256`・`checks_sha256` を実ファイルから計算）で束縛し、`dataset_split g0` が scale・ブロック完全性・seedブロック・test範囲ロックを**行から再計算**して pass/hold/fail を出す。自己申告では合格しない（`docs/m12-dataset-split-and-g0.md`）。
- 評価試合の記録（§5.3）と学習データは seedプール・用途が異なる（§2.1）。同一ファイルを両用しない。

### 6.1 未決定の扱い

- 未決定項目に依存する評価は、依存が解消するまで**正式判定を実施しない**（機能検証・パイロットは可。強さの主張は不可）。
- 未決定を理由に評価条件を後から変更して目標未達を隠さない（ロードマップ§8）。
- 本書の決定済み事項（P1〜P5、§2〜§5の規約）も、ロードマップ・公式ルールと相違が見つかった場合は正本を優先し、相違を報告する。
