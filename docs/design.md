# アグリコラ対戦AI 設計メモ

2026-11-04 作成、同日に設計レビューを反映。目的は『アグリコラ リバイズド』（2016年改訂版）の対戦AIを作ること。

最重要原則：ルールエンジンの正確性を維持しながら、AIの意思決定部分を自由に交換できる構造にすること。M1の時点でAIを複雑にする必要はないが、M2〜M5への拡張時にルールエンジンを作り直す設計は避ける。

## 基本方針

- ルールの正本はアグリコラ リバイズド。2007年旧版のルールと混ぜない。別製品『アグリコラ：ファミリーバージョン』のルールとも区別する。
- 目的関数：他のプレイヤーに勝つことが第一、高得点は第二。ただし勝敗と得点差の単純な加算では辞書式の優先順位にならないため、M3では勝率と得点差を別々に保持し、勝率を優先、勝率が同等と判定される場合に得点差を比較する（同等の条件はM3実装時に定義）。多人数戦では首位獲得確率を優先し、自分の得点最大化と混同しない。
- ルール解釈が不明な場合は推測で実装せず、公式ルールの該当箇所・選択肢・影響をIssueに記録して人間の判断を待つ。

## 段階

### M1：2人戦シミュレーター
- 基準はリバイズド版の手札なし初心者向けバリアント。職業・小改善カードは使わない。主要改善は使用する。公式バリアントのスタートプレイヤー用スペースの変更を反映する。Side Jobは実装しない（確定）。追加アクションスペースは設定で切り替えて実装する（詳細は「M1の確定仕様」）。
- ゴール：2人戦を全14ラウンド正確にシミュレーションし、ランダムAI同士で完走・得点計算・完全再現できること。実装の正確性を最優先とし、高度なAIやUIは作らない。
- 範囲：収穫（ラウンド4・7・9・11・13・14の後）、家族増員、部屋・改築、柵・厩、畑・種まき・パン焼き、家畜（羊・猪・牛）、主要改善10種、最終得点計算まで。

### M2：評価関数AI
- 評価項目の候補：食料の安全度（次の収穫までの必要量との差）、家族数の進捗、部屋の材質と数、畑・牧場の埋まり具合、資源の換算価値、最終得点への寄与見込み。
- 強さは対戦勝率で測る。階段はランダム ＜ 貪欲 ＜ 評価関数。

### M3：MCTS
- M1のシミュレーターの上にモンテカルロ木探索を載せる。プレイアウト方針にM2の評価関数を混ぜる。
- 未公開のラウンドカード順序は、内部状態から漏らさず、探索ごとにサンプリングする。
- 目的関数は勝率優先の辞書式（上記）。

### M4：3〜4人対戦＋人間対CPUの対戦UI
- 到達目標：人間1人 vs CPU3人で対戦できる形。簡易UIを用意する。CPUの強さはM2〜M3のAIを使う。
- 3〜4人戦用タイル（家畜市場・家族増員の2択）にも対応する。追加アクションスペースの設定はUIから変更できるようにする。
- 人数で変わるのはアクションスペースの構成と供給量。プレイヤー配列やボード構成を人数パラメータで持てば、拡張はデータ追加が中心になる。
- 多人数では目的関数が「首位獲得確率の最大化」に変わる。

### M5：職業・小改善カード、非公開情報への対応
- 効果の差し込み口（イベント／トリガー方式）をM1の設計に入れておく。カードは「タイミング＋効果」のデータと小さな処理の組み合わせで表現し、1枚ずつテスト付きで追加する。
- 追加順はリバイズド版の収録セットを単位とする。実装したカードだけで配布するモードを用意し、未実装カードは混ぜない。
- 手札が非公開情報になるため、探索は非公開情報に対応した手法が要る。ISMCTSを必須とはせず、ISMCTS等を比較検討する。観測状態のAPI（下記）が前提になる。

## 設計原則（後付けすると作り直しになるもの）

1. **ルールエンジンと意思決定を分離する**：細部の自動処理をエンジンに組み込まない。処理は「合法なアクションスペースの列挙 → AIまたは人間によるアクション選択 → 細部決定ポリシーによるパラメータ生成 → エンジンによる合法性検証 → 状態の更新とログ記録」の構造にする。細部決定ポリシーの対象は、柵の形・畑の配置・種まきの配分・家畜の配置・改築の詳細など。M1では単純なヒューリスティクスでよいが、将来は定石ライブラリ・評価関数・MCTS・人間の直接入力に差し替えられるようにする。エンジンは外部から指定された合法的な配置を受け付ける設計にする。
2. **内部状態とAIの観測情報を分離する**：完全な内部状態には未公開ラウンドカードの順序も保持するが、AIには公開済み情報しか渡さない。観測状態を取得するAPIを設ける。内部の乱数シードを利用して未来の情報を知ることを禁止する。
3. **状態は最初から多人数前提にする**：プレイヤーを配列で持ち、2人専用の前提をコードに埋めない。
4. **カード効果の差し込み口をM1で用意する**：ファミリー（初心者バリアント）では未使用でも、アクション処理を「共通処理＋効果フック」で組む。
5. **状態のコピーと巻き戻しを速くする**：MCTSのプレイアウト速度はここで決まる。イミュータブルな状態＋差分適用か、軽いディープコピーが候補。
6. **完全再現性を仕様で固定する**：下記のログ仕様に従う。
7. **ワーカーを使わない操作を別系統で用意する**：通常のワーカー配置アクションとは別に、任意タイミングの食料変換・家畜の再配置・資源の廃棄などを扱う仕組み（フリーアクション）を用意する。実行可能なタイミングと合法性は公式ルールに従う。M1では自動決定でもよいが、将来はAIと人間が選択できる構造にする。

## M1の確定仕様（2026-11-04 最終レビュー）

- **ゲームモード**：M1はリバイズド版の手札なし初心者バリアントを基準とする。Side Jobと2人用追加アクションスペースは別のオプションとして扱う（下記の通り確定）。
- **Side Job**：実装しない。
- **追加アクションスペース**：公式リバイズド版に準拠して実装する。
  - ゲーム設定 `additional_action_space_enabled` でON/OFFを切り替えられるようにする。初期値はOFF。
  - M1では2人戦用タイルの4択（林・資材市場・家畜市場・家族増員）に対応する。
  - 4択のうち1つを使用すると、同ラウンドの残り3つも使用不可になる。
  - 林は毎ラウンド木材1が累積し、林以外が選ばれても木材は保持される。
  - 家族増員はラウンド5以降、空き部屋がある場合のみ使用可能。
  - 設定値は対戦開始時に固定し、保存データと対戦ログに記録する。
  - ON/OFF両方の設定で固定シード対戦・ルールテスト・再現性テストを実施する。
  - M1ではUIを作らず、設定ファイルまたは起動引数で切り替える。M4ではUIから変更できるようにし、3〜4人戦用タイル（家畜市場・家族増員の2択）にも対応する。
- **初期状態**：各プレイヤーは木の部屋2つ、家族2人で開始する。開始プレイヤーはシード付き乱数で決定し、開始プレイヤーの食料は2、他プレイヤーは3とする。
- **勝敗判定**：最終得点が同点の場合、手元に残った建築資源（木・粘土・葦・石）の合計で順位を決める。それも同数なら同順位とする。テストにも追加する。

### ログと再現の仕様
- 記録する情報：ルールバージョンとゲームモード、初期状態・開始プレイヤー、ラウンドカード用乱数シード、AIの行動選択用乱数シード（用途別に分ける）、全アクションと細部の選択内容、各アクション前後の状態ハッシュ、ログ形式とエンジンのバージョン。
- 状態の保存・復元では乱数生成器の現在状態も保存する。
- 同一の初期条件とアクション列から、AIの判断を再実行しなくても同一のゲーム状態を復元できること。

## ルールテストの方針

- 固定テストの対象：家族増員（部屋の条件、最大5人、新生児の行動開始）、スタートプレイヤー（取得条件と次ラウンドへの反映）、複合アクション（処理順序、任意・必須の区別）、部屋・改築（建築条件、必要資源、全室改築）、畑（耕作、種まき、収穫、作物の残量）、柵（形状、閉鎖条件、隣接、15本上限）、厩・家畜（収容能力、異種混在、ペット、繁殖）、主要改善（10種の購入条件、効果、食料変換、得点）、給餌（通常家族2食料、新生児1食料）、物乞い（不足時の処理、1枚につき−3点）、最終得点（全カテゴリ、減点、上限、カード点）、勝敗判定（同点時は建築資源の合計、それも同数なら同順位）、追加アクションスペース（設定ON/OFFの両方、4択の排他、林の累積と保持、家族増員の条件）。
- すべての状態更新後に不変条件を検査する。例：資源数が負にならない、農場15マスに不正な重複がない、使用済みアクションスペースを再使用できない、家族・柵・厩の個数上限を守る、家畜の配置と収容数に矛盾がない。
- 固定テストに加え、ランダムな合法手を繰り返すテストも実施する。
- 各機能のPRには対応するルールテストを含める。テストの実装を最後まで先送りしない。

## 評価の分離

次の3項目を分離し、ランダムAIの平均スコアを人間の平均スコアと直接比較して合否判定しない。

- **ルールの正確性**：公式ルールとの照合、固定テスト、不変条件によって判断する。
- **シミュレーターの安定性と速度**：固定シード100試合の完走、再現性、平均実行時間によって判断する。
- **AIの強さ**：M2以降、ランダムAI・貪欲AI・評価関数AIの対戦勝率で比較する。

人間のスコア分布は異常検知の補助としてのみ用いる。

## 追加の検討事項

1. **分割アクションの扱い**：1手の中の細部選択を全部探索木のノードにすると分岐が爆発する。先行例（Rust実装）は一部のサブアクションをローカル処理で自動化して逃げた。この設計メモでは、細部は細部決定ポリシーに分離し（設計原則1）、ポリシーの候補を絞れる領域（柵など）は将来マクロアクションとして探索に戻せるようにする。
2. **MCTSだけでは深い戦略に届かない可能性**：先行例では、探索量（1手あたり2万状態）では人間の定石「家族を先に増やして手数を最大化する」が発見されず、小家族のまま農場と柵で45〜50点を取る別解に寄った。評価関数やプレイアウト方針の補助（M2）を探索の前提として考える根拠になる。
3. **検証の外部基準**：自己対戦の平均スコア分布を、人間の実プレイの知見（2人で45〜50点は好成績、4人で30〜40点）と照合する。ただしこれは異常検知の補助であり、合否判定には使わない（評価の分離を参照）。
4. **人間が打てる盤面**：AIの弱点は自己対戦だけでは見えない。M4で用意する。
5. **権利面**：ルールやカードの実装は個人利用が前提。リポジトリは公開とするが、入れてよいのは自作コードと自分の言葉の要約までとし、ルールブックのPDF、カード画像、カードテキストの丸ごとデータは入れない（先行リポジトリには「実物を所有していることが利用条件」という例もある）。
6. **テキストデータの2分類**：(a) UI表示用の名前と短い説明（アクション名、主要改善10種の名前と効果、得点内訳）はM4で必要だが、量が少なく自分の言葉で書けるため公開リポジトリでも要約の範囲に収まる。(b) カード原文のデータベースが必要になるのはM5で、これは公開側には入れず、必要なら非公開に分ける。実装コード（効果のロジック）と表示テキストは分離して設計する。

## 定石の扱い

細部の自動処理を「場当たりのヒューリスティクス」ではなく、人間の定石のライブラリで置き換える。特に柵・牧場は形のパターンが決まっている領域で、効果が大きい。ただしM1〜M3では必須にしない。

- 柵・牧場の定石の例（本人の挙げたもの）：序盤は4本で1マス牧場を作り羊＋かまど、9本で2牧場（繁殖用）、終盤は8マス15柵の形。
- 入れる場所は3か所：
  1. **候補生成**：柵アクションの細部を「どの定石を進める／完成させるか」の候補に絞る。候補が少数なら、細部も探索木に戻せる（マクロアクション化）。
  2. **プレイアウト方針**：ランダムに打つ代わりに定石へ寄せて打つ。MCTS単独では深い戦略が見つからなかった先行例への対策になる。
  3. **評価関数の特徴量**：定石への近さ・完成度を数値化して入れる。
- 柵以外の定石（家族を増やすタイミング、改築の順序、食料確保の型）も同じ枠組みで追加できる。定石はデータとして持ち、コードに埋めない。
- 細部決定ポリシーの自動処理側の方針（本人の考え）：配置や種まきは、少ない手番・少ないアクションで多くを実行できる形を優先する。
- データの入手性（2026-11-04 確認）：囲碁のような機械可読の定石データセットは存在しない。本人も提供できないため、定石は後付けで2経路から作る。(a) 戦略ガイド記事（日本語noteやBGGの戦略まとめには「柵15本で6マス4牧場」「8マス3牧場」等、目標とする最終盤面の形が文章で書かれている）をLLMに読ませ、テンプレート＋条件のデータに変換する。(b) 強い自己対戦のログから、高得点対戦に頻出する盤面の形を抽出する。BGAのリプレイを一括取得できる公式手段は見当たらない。

## 参考文献・先行例

- **Rust製アグリコラAI（先行実装と学びの記事）**：基本ゲーム＋MCTSで中級者レベルに到達。2人で45〜50点、4人で30〜40点（1手あたり2万状態の探索）。分割アクションの処理、非公開情報の扱い（プレイアウト中に開示し、事前に決まった盤面を使わない）など、今回の設計と論点がほぼ重なる。 https://hsaikia.github.io/agricola-ai/
- **jack-and-rozz/agricola（Python、改訂版、AI学習用）**：状態をJSONで表現し、`current_event` で「今求められている行動」を渡すイベント駆動の設計。職業・小改善をIDで管理。2017年のもので家畜管理などが未完だが、状態表現の参考になる。元は e2crawfo/agricola のフォーク。 https://github.com/jack-and-rozz/agricola
- **florian-rabe/Agricola**：ソロプレイの手筋検証用のロジック実装。記録挑戦用途。 https://github.com/florian-rabe/Agricola
- **Cowling, Powley & Whitehouse (2012) "Information Set Monte Carlo Tree Search", IEEE Transactions on Computational Intelligence and AI in Games**：ISMCTSの原論文。M5で手札が非公開情報になるときの基礎。
- **Whitehouse (2014) ヨーク大学博士論文 "Monte Carlo Tree Search for Games with Hidden Information and Uncertainty"**：非公開情報ゲームでのMCTSの拡張のまとめ。
- **Szita, Chaslot & Spronck (2010) "Monte Carlo Tree Search in Settlers of Catan"**：ユーロゲームへのMCTS適用の先行研究。アグリコラと同じく多人数・スコア勝負のゲームでの探索の工夫が参考になる。
