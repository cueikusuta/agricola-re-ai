## 1. 目的と開発原則

目的は次の2つを並立させる。

1. **人間が遊べるアグリコラ**：リバイズド2016、2〜4人戦、平易な日本語UI、手動詳細操作、段階的に増やすA〜Eカード、7-7・10-7ドラフト、人間対CPU。できる限り画面切替・モーダル等で表示を整理し、スクロール依存を抑える。
2. **強い対戦AI**：正確なルールエンジン、高速自己対戦、探索、カード・ドラフト評価、段階的な自己対戦学習、再現可能な強さの測定。最終目的は**首位を獲得する確率**を高めること。期待順位・得点差・計算コストは順に補助指標とする。

人間の棋譜・定石の提供は必須としない。学習データは合法な自己対戦・探索から生成する。公式カード原文・画像を公開リポジトリに収録しない。AIの観測とゲーム内部状態を厳密に分離し、再現性を維持する。Side Jobは実装しない。追加アクションスペースは既存仕様に従いON/OFF設定を維持する。

## 3. AIの暫定評価基準（今回の決定）

| 項目 | 初期設定 | 意味・留意点 |
|---|---|---|
| **強さの改善目標** | **首位率 +5パーセントポイント** | `新AI首位率 − 比較対象AI首位率 >= 0.05`。**相対5%改善ではない**。同一ルール・カードプール・対戦相手構成・思考時間予算で比較する。 |
| **人間対戦での1手の思考時間上限** | **10秒** | AIのアクション種類・詳細決定を含めた1手。原則、制限時間内に最善の候補を返し、上限到達時は保存済み合法候補へフォールバックする。描画停止や操作不能を招かない。 |
| **初期評価規模** | **1,000試合** | まず各候補AIにつき1,000試合を初期評価バッチとする。未測定の比較対象AIには同条件・同数の対戦を追加するため、比較全体では2,000試合以上となり得る。座席と初期条件を均等化する。 |
| **統計判定** | **95%信頼区間を併記** | 点推定だけで合格にしない。差の95%信頼区間が0を跨ぐなら「改善傾向／判定保留」。必要試合数を再推定して増やす。 |
| **意思決定の基本順位** | **首位率 → 期待順位 → 得点差 → 計算コスト** | 首位率の差が統計的に判別できない場合は期待順位（小さいほど良い）・得点差・計算コストを順に参考にする。ただし有意差がないことを同等性の証明と混同しない。得点差だけで強いAIと断定しない。 |

### 3.1 首位率の定義と比較条件

- **首位**：最終順位で1位となること。公式に準じた同点時の資源タイブレーク適用後も同順位の場合、**同率1位は各プレイヤーへ `1/k` の勝利クレジット**を付与する（`k` は同率首位者数）。これを評価用の「首位率」とする。参考値として「同率首位を含む首位到達率」「純粋な単独1位率」、平均順位も分けて記録する。**これは評価上の勝利クレジットの定義であり、公式ルールの順位判定を変更しない。**
- **2人戦**：座席交換ペアを基本単位とし、同じ初期条件・カードモード・相手AIで候補と既存AIを比較する。
- **4人戦**：候補AIが座る席を4席均等化し、残り3席の相手AI構成を固定する。候補／既存AIを同一条件の試合群で比較する。全員を別版AIに入れ替えた試合を、候補単体の比較と混同しない。
- **共通**：ルールエンジンSHA、デッキ版、ドラフト方式、追加タイル設定、相手AI版、座席、乱数シード、思考時間またはCPU予算、ハードウェア条件を記録する。学習・チューニングに使わない未知シードを最終評価用に確保する。
- **主要比較**：同じ評価条件の新旧AIで、首位率の差（**絶対値のパーセントポイント差**）、期待順位差、得点差を別々に報告する。カードなし/あり、2人/4人、7-7/10-7は別の評価条件として扱い、結果を無条件で合算しない。

### 3.2 信頼区間・必要試合数・合否判断

1. 初期1,000試合は**計測開始点であり、+5ポイント改善を確定させるための固定試合数ではない**。
2. 同一シード・座席交換で新旧を対応させた場合、**シード単位のペアを1ブロック**として差の95%信頼区間をブロック・ブートストラップで推定する。座席だけを独立試合として数え上げ、精度を過大評価しない。採用する手法・反復数を評価コードに固定して記録する。
3. 補助的に各AIの首位率について95%区間を併記。単純な二項分布近似だけで、複数座席・同点・共有シードによる相関を扱ったことにはしない。
4. 合格は原則、**点推定で +5ポイント以上**かつ**改善差の95%信頼区間下限が0を超える**こと。+5ポイント自体を統計的に保証したい強い判定が必要なら、**区間下限も+5ポイント以上**という別基準を用いる（通常の採用条件にはしない）。
5. 区間が0を跨いだ場合は「判定保留」。観測したばらつき・効果量から、検出力80%、両側有意水準5%を例とする**必要試合数を再計算**し、増分試行を実施する。途中の結果を見て無制限に検定を繰り返さず、追加計測の上限・判定時点を事前に決める。必要に応じ逐次検定に切り替える。
6. **参考値**：独立な二つの勝率をそれぞれ50%付近として比較し、差5ポイントを80%の検出力で検出する単純近似では、**各群約1,600試合**が目安。実際のアグリコラは4人戦・同率・座席相関・ペア設計・相手構成で必要数が変わるため、この数を固定基準にしない。
7. +5ポイント未達でも、思考時間の大幅削減や別モードでの改善などは別指標として記録する。ただし**首位率目標を達成したことにはしない**。

### 3.3 10秒上限の計測

- 測定対象は**対戦中のCPUの1回の意思決定**（ワーカー配置・カード・資源・配置などの詳細決定を含む）。ドラフトの1ピックも独立した意思決定として同じ上限で評価する。オフライン学習や大量バッチ試合にはこの制限を適用しない。
- 評価用の基準PC／CPUと実行モード（例：Rust release）を固定し、平均・中央値・p95・p99・最大値、タイムアウト率、フォールバック率を記録する。最終受け入れでは**観測した全手で10秒以内**を要求し、超過しそうな場合は時間予算に基づく停止・合法手フォールバックを行う。
- 検索開始前から**必ず合法な初期候補**を確保し、期限切れ時にその候補へフォールバックする。期限切れ時に未確定の不正手やパニックを返さず、ブラウザ操作をブロックしない。ハードウェア差により結果が変わるため、環境と測定時刻を記録する。
- M13以降の探索比較では、**同じ時間予算の比較**を主要結果にする。シミュレーション回数固定比較は補助指標。

### 3.4 学習・探索の報酬と最終評価は分離する（Muse版から採用）

- **最終評価の優先順は「首位率 → 期待順位 → 得点差 → 計算コスト」**。首位率を主要成果とし、下位指標を理由に首位率の悪化を隠さない。
- **学習・探索で使う報酬は実験対象**。初期候補として `自分の最終得点 − 他プレイヤーの最終得点の平均` を使用できる。報酬が連続値なので教師信号を得やすい一方、4人戦では「得点差は大きいが2位」の手を過大評価し得る。**学習目標＝最終目的と誤認しない**。
- M13/M14では少なくとも **(A) 首位クレジット、(B) 得点差、(C) 首位・順位・得点差を併用した候補** を同じ評価条件で比較する。重みや順位報酬は検証セットではなく学習・調整用セットで決める。首位率を改善できない代理報酬は採用しない。
- 旧M7の探索報酬や過去の評価結果は履歴として保持し、M13の比較対照に使う。現行コードの目的関数を、本計画採用だけを理由に無条件変更しない。

### 4.1 M8のルール正確性：完走試験とは分けて判定する

**1,000試合完走は安定性の試験であり、ルール正確性の証明ではない。** 次の3系統を別のCI・報告項目として持つ。

1. **公式ルールに基づく期待結果テスト**：各アクション・収穫・給餌・得点・人数別アクション・追加タイル・カードの発動時点・複合効果を、固定入力と期待状態で照合する。ルールの解釈が曖昧ならIssueへ隔離し、推測実装しない。
2. **不変条件・性質テスト**：資源の負数、農場15マスの重複、使用済みスペースの再利用、合法でない家畜配置、手札秘匿、任意操作の無限ループなどを検出する。ランダム合法手・境界条件・保存復帰・再演ハッシュを検証する。
3. **対戦完走・速度試験**：サポートするゲームモードを明示して固定seed 1,000試合を実行。初期状態、ラウンド、カード構成、勝敗、異常理由、エンジンSHA、実行時間を記録する。**4人戦のカードありモードを、M10の十分なカードプール整備前に必須合格としない。**

受け入れ条件の「サポート対象組合せ」はテスト一覧に明示し、カードなし2/3/4人、検証済みカードあり（必要枚数と人数条件を満たす人数のみ）、追加タイルON/OFFを区別する。

### 4.2 M8の合法詳細行動API：人間とAIの責務を分ける

> 方針：**全合法手を表現・検証できる**ことと、**全合法手を探索時に一括列挙する**ことは別。

```text
ゲーム状態
   ↓
利用できる行動の種類を問い合わせる（例：柵・畑・職業）
   ↓
段階的な詳細入力インターフェース
   ├─ 人間UI：全合法の詳細選択を入力可能（複雑な場合は段階的選択）
   └─ AI：候補生成器が有望な詳細案を少数提案（マクロアクション等）
   ↓
共通エンジンの合法性検証 → 状態更新 → 再演ログ
```

- `SimpleDetails`は既定の自動入力ポリシーであり、**合法行動集合の定義ではない**。合法な柵・畑・種まき・家畜配置・部屋・改築・給餌・変換の詳細を別の入力でも表現できる。
- ルールエンジンは、AIが提示しなかった合法手でも正当に受理する。人間の操作とAIの行動は同じ検証器を通す。
- 大きな分岐がある詳細操作は段階的に候補・制約を問い合わせ、AI探索側のみビーム幅・候補数・定石パターン等で枝刈りする。**探索候補外を不正手とみなさない**。
- フリーアクションは発動可能タイミング・回数・資源変換・取り消し前の仮入力を検証する。非公開情報が候補生成器や状態コピーから漏れないようにする。
- テストでは既知の合法詳細手の受理と、代表的な不正詳細手の拒否を両方確認する。特に`SimpleDetails`が作らない合法配置を含める。

### 4.3 M10のカード枚数は「適法に配れる枚数」で判定する

- **最低ライン**：4人10-7の初期配布を成立させるため、実装済み・公式照合済み・4人戦で使用可能な**職業40枚／小改善40枚**を確保。職業の人数制限等によって実際に配布できないものはこの数に入れない。
- **実戦向け初期目安**：それぞれ**80枚以上**。同じ組み合わせの繰り返しを避けるための目安であり、80枚を実装しただけで「バランス完成」とは判断しない。
- **数量以外の品質**：即時・常時・条件付き・終了時得点などの効果系統、職業の人数条件、発動タイミング、コスト、相互作用を記録する。効果実装率をカードID数と別指標で集計する。
- **未実装・要公式照合**はデッキ生成から除外。A〜E840枚の台帳は調査の起点であり、カードテキスト原文を公開リポジトリへ追加しない。

### 4.4 M11のドラフト記憶（不完全情報AIの前提）

- ドラフト開始時の自分の候補カード、各選択、**自分から渡したカード**、途中で受け取ったカード、後で公開されたカードを、時系列に観測履歴として残す。
- 相手が後で選んだカードは、**公開された、または自分の観測履歴から論理的に推定できる範囲**だけをAIに渡す。内部の完全手札配列から直接取得しない。
- 観測APIは、現在の手札と現在の公開情報だけでなく、**正当に観測した過去情報と残り手札枚数**を表現できる形式にする。再演・保存復帰で履歴の整合性を検証する。
- 7-7・10-7それぞれについて、配布枚数、選択数、左右の受け渡し、何枚を保持するか、全員同時か順番かをルール文書で確定する。**10-7同時ドラフト／10-7非ドラフト選択は異なるルールモードとして混同しない。** 実装可能だからといって独自ルールを既定にしない。

## 6. 横断的な開発・CIルール

1. **公式ルールとの整合**：正本はリバイズド2016。解釈が曖昧なカードはIssueへ隔離し、確定まで配布不可。カード相互作用・発動時点・任意／強制選択もテストする。
2. **再現性・非公開情報**：ゲーム内部状態と観測APIを分離。初期条件、seed、ドラフト履歴、細部決定、状態ハッシュ、エンジン・カード版、AI版を保持。未知情報をAIへ渡さない。
3. **合法性と候補生成の分離**：合法性はRustエンジンの共通検証器が担当。人間UIの詳細入力を、AI向け候補生成器の能力で制限しない。
4. **レビュー手順**：1 Issue = 1目的 = 1ブランチ = 1PR。処理のまとまり、関数、コミットの単位で自己レビューし、問題・改善点を修正。重要なルール変更は独立AIレビューも検討。
5. **CI**：通常PRの軽量必須ゲートは**60秒以内が目標**。変更ファイルに応じて関連テストを選ぶが、必要なルール・セキュリティ検証を省略しない。大規模1,000試合評価、Playwrightフル14ラウンド、大量ベンチマーク、学習は別ジョブで実行可能にする。少数のブラウザ・スモーク試験を通常CIに残す方針を検討する。**大量シミュレーションは原則GitHub Actionsの専用ワークフローで実行**し、通常CIに負担をかけない。
6. **計測の記録**：対戦モード、対戦相手、試合数、首位率・同率首位・期待順位・得点差、95%区間、試合/秒、意思決定/秒、1手のp95/p99/最大、CPU費用、観測したタイムアウト率を記録する。数値の改善だけでルールの正しさを判定しない。
7. **コスト管理**：まずCPUで小規模実証。改善の統計的根拠と試合速度を確認してから計算規模を拡大する。追加試合数は検出力計算と計算予算を踏まえて調整。
8. **大量シミュレーションの実行場所（2026-11-06決定）**：M8のモード別1,000試合、M12以降のバッチ自己対戦・AI間比較、M13以降の探索比較に伴う大量試合は、**原則としてGitHub ActionsのGitHub-hosted標準CPUランナー**で実行する。ローカルPCは少数試合のスモークテスト、故障再現、実装・デバッグに使用し、長時間の本番計測をローカル実行の前提にしない。M8-3（#110）で通常CIとは独立した手動起動（`workflow_dispatch`）ワークフローを実装し、試合数・モード・AI・シード範囲・並列分割数を入力可能にする。最初は少数ジョブで性能・費用・キューを測定し、同時実行上限内で並列度を調整する。各ジョブに**重複しないシード区間**を割り当て、対戦/座席ローテーションのペア・ブロックを壊さず分割する。結果はJSON/CSV等の機械可読GitHub Actions Artifactへ保存し、ジョブ条件、コードSHA、ルール/カード/AI版、ハードウェア、失敗ログ、所要時間を残す。集約時に件数と重複seedを検証し、失敗時は結果を成功扱いにしない。公開リポジトリの標準ランナーの無料利用条件は利用時点で確認し、不要な長時間ジョブや無断の有料ランナー/GPUを起動しない。GPU学習は必要性と費用対効果が判明した時点で別途判断する。既存のCIと競合する過剰な並列実行は避ける。
9. **ドキュメント同期**：計画採用後、`docs/design.md` の従来「M8以降：公開」の記載を歴史として残しつつ、**現在採用するM8以降の工程を明示的に追記・更新**。`AGENTS.md` とIssueから正本が参照できるようにする。

### 9.1 Issue単位で守る進め方

- **1 Issue = 1目的 = 1ブランチ = 1PR** を原則とする。1つのIssue内の実装が肥大化する場合は実装開始前に分割し、相互依存をIssueに記載する。
- 作業開始時に **対象モード、スコープ外、変更API、受け入れテスト、計測条件、依存するPR** を確認する。新しいカードルールの疑義はIssueで止め、独自解釈で進めない。
- **処理のまとまり・関数・コミットごとに自己レビュー**し、発見した問題をその場で修正する。必要なCIを確認し、失敗があれば対応。CI待機中は別の独立タスクを進めてよいが、未検証の状態でマージしない。
- 通常CIが60秒目標を超えた場合、実測・影響範囲を記録して高速化する。**1,000試合の大量実行・AI自己対戦は原則GitHub Actionsの独立ワークフロー**として実行し、長時間Playwright完走・学習ジョブも通常CIから分離して結果リンクをPRに貼る。
- テストに合格しても、**実ブラウザの14ラウンド完走は別ゲート**。APIテストだけで人間の操作性の完了を宣言しない。

### 9.2 終了・保留の扱い

- **各工程は明示した受け入れ条件を満たして初めて完了**。未実装カード・未解決の公式照合・未計測の4人モードは実装済みとして数えない。
- 研究工程（M13〜M15）で「+5ポイント」が達成されない場合、研究結果・失敗条件・次の仮説を記録し、**その目標が未達であることを明記**する。正確性やUIを犠牲にして達成したことにしない。
- 他のAIに引き継ぐときは `AGENTS.md` → `docs/design.md` → 本書 → 対象Issue → 関連PRの順に読み、ルールと現在の工程を混同しない。
